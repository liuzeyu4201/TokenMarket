# V0.2 测试与发布验收总则

## 1. 发布原则

V0.2 只有在功能、协议兼容、容量、可靠性、安全、可访问性和运维证据全部满足后才能标记可上线。测试通过必须可复现；口头确认、单次手工冒烟或仅看覆盖率不能替代验收。

## 2. 必测层级

- 单元与属性测试：金额精度、状态机、路由过滤/评分、权限和协议字段。
- 契约测试：三厂商端点目录、错误、流式、工具调用、未知字段和资源生命周期。
- 集成测试：PostgreSQL、Redis、事件投递、幂等、迁移和服务间契约。
- E2E：公开站点、注册登录、买卖双方、管理员、共享/专享代理和账务闭环。
- 并发/竞态/模糊测试：会话替换、额度预留、连接占用、回调重放、协议解析。
- 性能/压力/耐久：500 RPS、1000 RPS burst、500 长连接、2 小时 soak。
- 韧性/恢复：节点、Redis、数据库、队列、upstream、发布与回滚故障注入。
- 安全：SAST、依赖/镜像/秘密扫描、DAST、白盒、黑盒和独立渗透测试。
- 浏览器与可访问性：关键浏览器、响应式、键盘、读屏语义、WCAG 2.2 AA。

## 3. 硬门禁

| 项目 | 发布门槛 |
|---|---|
| 需求与验收映射 | 100% 有测试或人工证据 |
| 稳定端点目录 | 100% 有合同测试且通过 |
| 关键 E2E | 100% 通过 |
| 变更领域行覆盖率 | ≥ 80% |
| 鉴权/路由/权限/账本分支覆盖率 | ≥ 90% |
| P0/P1 缺陷 | 0 |
| P2 缺陷 | 必须书面接受、负责人和期限 |
| 安全 Critical/High | 0 |
| 安全 Medium | 必须书面接受、负责人和期限 |
| 关键自动化 | 连续 3 次无 flaky 通过 |

最终候选版本还必须完成一次全量容量、恢复、迁移与回滚演练。独立渗透测试必须在公开发布前完成；发现修复后需要复测证据。

## 4. 证据格式

每个 SF 保留 requirement → test case → result → artifact 的追踪关系。证据包含版本/commit、环境、时间、执行命令、配置摘要、原始结果位置和负责人。失败重跑必须保留首次失败原因，禁止只保留最后一次绿色结果。

## 5. 发布与回滚

发布评审必须列出：范围、已知风险、数据库/契约兼容性、容量余量、SLO 仪表盘、告警负责人、逐步放量、停止条件和回滚步骤。回滚后账务事件和数据库 schema 必须保持可读，不能以删除数据恢复服务。
