### 1.2 服务职责详述

#### 1.2.1 proxy-gateway（Go）

| 模块 | 职责 | 为什么用 Go |
|------|------|-------------|
| **API Key 接入层 (L1)** | 校验买家传入的代理 Key，解析 Key 中的平台标识和额度信息 | Go 的高并发性能适合 API 网关场景 |
| **代理 Key 生成 (L2)** | 为买家生成平台特定的代理 Key，关联卖家原始 Key | 计算密集型操作需要低延迟 |
| **智能路由 (L3)** | 根据目标平台、Key 可用额度、卖家在线状态选择最优转发路径 | 需要毫秒级决策 |
| **实时计量 (L4)** | 请求前后计量 tokens，实时扣减额度，超限拦截 | 高频计数操作需要极致性能 |
| **健康检查** | 定时探测各目标平台和内部服务的可用性 | 轻量级协程适合定时任务 |

**设计理由**：网关是整个系统的流量入口，Go 的 goroutine 模型在处理高并发 API 请求时比 Python 有数量级优势。单人开发时，网关逻辑相对独立，用 Go 编写后后期几乎不需要改动。

#### 1.2.2 api-service（Python/FastAPI）

| 模块 | 职责 | 说明 |
|------|------|------|
| **用户服务** | 注册、登录、JWT 签发、用户信息管理 | 三端共用用户体系 |
| **卖家服务** | Key 录入、额度上架、订单管理、收益查看 | 卖家端核心 API |
| **买家服务** | 额度购买、Key 获取、用量查询、余额提醒 | 买家端核心 API |
| **积分服务** | 积分充值、消费、冻结/解冻（Escrow）、积分流水 | 平台虚拟货币体系 |
| **通知服务** | WebSocket 实时推送 + 邮件/站内信异步通知 | 余额预警、订单状态变更 |

**设计理由**：业务逻辑复杂、迭代频繁，Python/FastAPI 开发效率高，类型提示 + 自动文档减少维护成本。单人开发时，把密切相关的业务聚合在一个服务中，避免过度拆分导致的运维负担。

#### 1.2.3 billing-service（Python/FastAPI）

| 模块 | 职责 | 说明 |
|------|------|------|
| **实时计量** | 接收网关的计量事件，实时计算 token 消耗 | Kafka 消费端 |
| **计费引擎** | 按平台差异化定价模型计算费用 | 各平台计费规则不同 |
| **Escrow 结算** | 买家确认或超时自动确认后，将冻结积分结算给卖家 | 资金安全保障 |
| **对账** | 日终对账，检测异常流水，生成对账报告 | 每日凌晨执行 |

**设计理由**：计费逻辑独立演化，与业务服务解耦。后期可以独立扩容、独立优化计费算法。V0.1 阶段虽然流量不大，但分离计费域为后续实时计费优化留足空间。

#### 1.2.4 admin-service（Python/FastAPI）

| 模块 | 职责 | 说明 |
|------|------|------|
| **用户管理** | 查询/冻结/解封用户，查看用户操作日志 | 管理后台专用 |
| **订单管理** | 查看所有交易订单，介入争议订单 | 仲裁功能 |
| **平台配置** | 系统参数、平台对接配置、费率调整 | 热更新配置 |
| **数据看板** | 交易量、用户数、平台分布等统计 API | 聚合查询 |
| **审核流程** | 卖家入驻审核、Key 审核 | 风控前置 |

**设计理由**：管理后台 API 与业务 API 分离，权限模型完全不同。后期可以独立部署在 VPN/内网环境中，增强安全性。

#### 1.2.5 web-frontend（React）

| 角色路由 | 职责 | 说明 |
|----------|------|------|
| `/seller/*` | 卖家端：Key 管理、额度上架、订单跟踪、收益提现 | 卖家工作台 |
| `/buyer/*` | 买家端：额度购买、Key 管理、用量查询、余额充值 | 买家控制台 |
| `/admin/*` | 管理后台：用户/订单/配置/看板管理 | 运营后台 |

**设计理由**：三端共用一套代码库，但路由隔离。单人开发时，组件、工具函数、API 客户端可以最大程度复用。通过角色鉴权控制页面访问，而非物理分离项目。

#### 1.2.6 共享包

| 包名 | 内容 | 使用方 |
|------|------|--------|
| **shared-models** | Pydantic 模型 / Go struct 定义，包含所有 DTO、Entity 基础结构 | 所有服务 |
| **shared-utils** | 通用工具函数：日期处理、ID 生成、加解密辅助、数据校验 | 所有服务 |
| **shared-constants** | 枚举定义、错误码、配置键名、平台常量 | 所有服务 |

**设计理由**：V0.1 阶段用 Git submodule 或文件复制方式共享，避免过早引入私有包仓库的复杂度。类型定义统一后，前后端对接效率大幅提升。

### 1.3 数据流示意

```
买家调用 AI API（携带代理 Key）
        │
        ▼
┌───────────────┐
│ proxy-gateway │ ← 校验 Key、路由到目标平台、计量 tokens
│   (Go)        │
└───────┬───────┘
        │ ① 转发请求到目标平台（智谱/火山/MiniMax/Kimi/Claude/GPT）
        │ ② 异步发送计量事件到 Kafka
        ▼
   目标平台返回
        │
        ▼
┌───────────────┐
│ billing-svc   │ ← Kafka 消费：实时计量、冻结积分扣减
│ (Python)      │
└───────────────┘
        │
        │ ③ Escrow 到期/确认后，结算给卖家
        ▼
┌───────────────┐
│ api-service   │ ← 积分账户更新、通知推送
│ (Python)      │
└───────────────┘
```

**目录职责说明**：
- `cmd/`：Go 项目惯例，main 包放在 cmd/ 下，支持多入口（如后续需要 CLI 工具）。
- `internal/`：Go 1.4+ 特性，internal 目录下的包不可被项目外 import，强制边界隔离。
- `internal/client/platform/`：**平台适配器模式**，每个目标平台一个文件，统一接口。新增平台时只需新增一个适配器文件。
- `internal/pkg/tokenizer/`：对接不同平台的 token 计数算法，国内平台通常有各自的计数规则。

## 三、服务间通信规范

### 3.1 通信方式总览

| 通信类型 | 场景 | 技术选型 | 原因 |
|----------|------|----------|------|
| **同步通信** | 服务间实时调用（如创建订单时查询积分余额） | HTTP RESTful API | 简单直观，调试方便，V0.1 阶段足够 |
| **异步通信** | 事件驱动（计量流水、订单状态变更、通知） | Kafka | 解耦生产者和消费者，支持重试和削峰 |
| **服务发现** | 容器间寻址 | Docker Compose 网络名 | 零配置，足够支撑单体服务器部署 |

### 3.2 同步通信：RESTful API

#### 3.2.1 服务间调用拓扑

```
┌──────────────────┐
│  proxy-gateway   │ ──(HTTP)──▶ api-service: 校验 Key、查询用户状态
│      (Go)        │ ──(HTTP)──▶ billing-service: 查询实时余额（少量场景）
└──────────────────┘
        │
        ▼
┌──────────────────┐ ──(HTTP)──▶ billing-service: 查询积分余额
│   api-service    │ ──(HTTP)──▶ billing-service: 创建 Escrow 记录
│   (Python)       │
└──────────────────┘
        │
        ▼
┌──────────────────┐
│ billing-service  │ ──(HTTP)──▶ api-service: 结算时更新用户积分
│   (Python)       │
└──────────────────┘
        │
        ▼
┌──────────────────┐ ──(HTTP)──▶ api-service: 查询用户/订单信息
│  admin-service   │ ──(HTTP)──▶ billing-service: 查询计量/对账数据
│   (Python)       │
└──────────────────┘
```

#### 3.2.2 服务间调用规范

| 规范项 | 规则 | 原因 |
|--------|------|------|
| **超时设置** | 连接超时 5s，读取超时 30s | 防止级联故障，AI API 响应可能较慢 |
| **重试策略** | 幂等操作（GET/PUT）重试 3 次，非幂等操作不重试 | 避免重复写 |
| **熔断降级** | 错误率 > 50% 持续 30s 触发熔断，30s 后半开 | 防止雪崩 |
| **请求头传递** | 必须透传 `X-Request-ID` | 全链路追踪 |
| **服务间认证** | 内部 API 使用 `X-Internal-Token` 简单校验 | V0.1 阶段防君子不防小人 |

#### 3.2.3 内部调用代码示例

```python
# api-service 调用 billing-service（Python 示例）
import httpx
from shared.constants import INTERNAL_TOKEN

async def get_credit_balance(user_id: str) -> int:
    async with httpx.AsyncClient(
        base_url="http://billing-service:8000",
        timeout=httpx.Timeout(connect=5.0, read=10.0),
        headers={"X-Internal-Token": INTERNAL_TOKEN}
    ) as client:
        resp = await client.get(f"/v1/credits/balance?user_id={user_id}")
        resp.raise_for_status()
        return resp.json()["data"]["balance"]
```

### 3.3 异步通信：Kafka

#### 3.3.1 Topic 设计

| Topic 名 | 生产者 | 消费者 | 说明 |
|----------|--------|--------|------|
| `meter.events` | proxy-gateway | billing-service | 每次 API 调用产生的计量事件 |
| `order.events` | api-service | billing-service, notification | 订单创建/确认/取消事件 |
| `credit.events` | billing-service | api-service | 积分变动事件 |
| `notification.events` | api-service, billing-service | notification-service | 通知触发事件 |

#### 3.3.2 消息格式

```json
{
  "event_id": "evt_123456789",
  "event_type": "meter.usage",
  "timestamp": "2026-07-12T10:30:00+08:00",
  "payload": {
    "proxy_key_id": "pk_xxx",
    "platform": "glm",
    "model": "glm-4",
    "input_tokens": 150,
    "output_tokens": 300,
    "total_tokens": 450,
    "duration_ms": 1200,
    "user_id": "u_xxx",
    "seller_id": "s_xxx"
  }
}
```

#### 3.3.3 Kafka 使用规范

| 规范项 | 规则 | 原因 |
|--------|------|------|
| **分区策略** | `meter.events` 按 `proxy_key_id` 分区，保证同一 Key 的计量顺序性 | 避免并发导致的余额计算错误 |
| **ACK 级别** | `acks=all`（生产环境） | 不丢消息 |
| **消费模式** | billing-service 手动提交 offset | 确保消息处理完成后再提交 |
| **死信队列** | 消费失败 3 次后转入 `*.dlq` topic | 人工介入排查 |
| **消息保留** | 7 天 | 足够支撑日终对账和故障恢复 |

### 3.4 服务发现

V0.1-V0.2 阶段采用 **Docker Compose 内置 DNS** 实现服务发现：

```yaml
# docker-compose.yml 片段
services:
  proxy-gateway:
    networks:
      - tokenmarket-net

  api-service:
    networks:
      - tokenmarket-net
    # 在 proxy-gateway 中通过 http://api-service:8000 访问

networks:
  token-market-net:
    driver: bridge
```

**为什么不用 Consul/Eureka？**

- 当前阶段所有服务部署在同一台服务器（或本地开发机）上，Docker Compose 的容器名即 DNS 名已足够。
- 引入服务注册中心会增加部署复杂度和学习成本，与"快速原型验证"的目标冲突。
- **扩展路径**：V0.3 引入 Kubernetes 后，自然过渡到 K8s Service 发现。

## 四、接口契约规范

### 4.1 统一 API 响应格式

所有 HTTP API（包括网关对外暴露的代理 API）必须遵循以下响应结构：

```json
{
  "code": 20000,
  "message": "success",
  "data": { ... },
  "request_id": "req_abc123def456",
  "timestamp": "2026-07-12T10:30:00+08:00"
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `code` | int | 业务状态码，见 4.4 错误码设计 |
| `message` | string | 人类可读的状态描述 |
| `data` | object / array / null | 响应数据体 |
| `request_id` | string | 全链路追踪 ID，由网关生成并透传 |
| `timestamp` | string (ISO8601) | 响应时间戳 |

**为什么这样设计？**

- `code` 与 HTTP status code 分离：HTTP 200 仅代表网络层成功，业务成功/失败由 `code` 表达。避免某些客户端库将非 2xx 响应直接抛异常。
- `request_id` 强制透传：出现问题时可按 ID 串联网关日志、各服务日志、数据库记录。
- `timestamp` 便于客户端排查缓存问题和时区问题。

### 4.2 分页规范

列表查询统一使用以下分页结构：

**请求参数**：

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| `page` | int | 否 | 1 | 页码，从 1 开始 |
| `page_size` | int | 否 | 20 | 每页条数，最大 100 |
| `sort_by` | string | 否 | `created_at` | 排序字段 |
| `sort_order` | string | 否 | `desc` | `asc` / `desc` |

**响应结构**：

```json
{
  "code": 20000,
  "message": "success",
  "data": {
    "page": 1,
    "page_size": 20,
    "total": 156,
    "total_pages": 8,
    "items": [
      { ... },
      { ... }
    ]
  },
  "request_id": "req_xxx"
}
```

**为什么 page 从 1 开始？**

- 产品经理、运营人员、甚至你自己查看数据时，默认理解都是"第 1 页"。offset/limit 虽然对程序员更直观，但 "page=0" 容易在前后端对接时产生歧义。

### 4.3 版本管理

| 规范项 | 规则 |
|--------|------|
| **版本路径** | `/api/v1/`、`/api/v2/` |
| **默认版本** | 不带版本号时默认路由到最新稳定版（V0.1 阶段只有 v1） |
| **版本升级策略** | 破坏性变更必须走新版本；新增字段可在当前版本追加 |
| **弃用公告** | 旧版本弃用前保留至少 3 个迭代周期（约 1-2 个月） |

**URL 示例**：

```
GET  /api/v1/seller/keys              # 查询卖家的 Key 列表
POST /api/v1/buyer/purchase           # 买家购买额度
GET  /api/v1/admin/users              # 管理后台查询用户
GET  /api/v1/credits/balance          # 查询积分余额
```

**为什么用 URL 路径版本而非 Header？**

- URL 更直观，调试时一眼可见版本。
- 前端、第三方接入者复制粘贴 URL 时不会遗漏 Header。
- 与大多数公共 API（GitHub、Stripe）保持一致，降低学习成本。

### 4.4 错误码分层设计

#### 4.4.1 错误码结构

错误码为 **5 位数字**，结构如下：

```
  1  x  x  x  x
  │  │  │  │  │
  │  │  │  │  └── 具体错误序号（00-99）
  │  │  │  └───── 错误子类别（0-9）
  │  │  └──────── 服务标识（0-9）
  │  └─────────── 层级标识：1=全局, 2-9=业务
  └────────────── 固定为 1（与 HTTP 状态码区分）
```

#### 4.4.2 全局错误码（1xxxx）

所有服务共用，由 `shared/constants/error_codes.py` 和 `error_codes.go` 统一定义。

| 错误码 | 含义 | 说明 |
|--------|------|------|
| 10000 | 成功 | 默认成功码 |
| 10400 | 请求参数错误 | 参数缺失、格式错误、校验不通过 |
| 10401 | 未授权 | Token 缺失、过期、无效 |
| 10403 | 权限不足 | 有登录但无操作权限 |
| 10404 | 资源不存在 | 请求的 ID 对应记录不存在 |
| 10409 | 资源冲突 | 唯一键冲突、状态冲突 |
| 10422 | 请求体格式错误 | JSON 解析失败、字段类型不匹配 |
| 10429 | 请求过于频繁 | 限流触发 |
| 10500 | 服务器内部错误 | 未预期的异常 |
| 10502 | 上游服务不可用 | 依赖服务超时或报错 |
| 10503 | 服务暂时不可用 | 熔断、维护中 |

#### 4.4.3 业务错误码（2xxxx-9xxxx）

| 服务 | 码段 | 示例 |
|------|------|------|
| api-service 用户/认证 | 20000-20999 | 20001: 用户名已存在, 20002: 密码错误, 20003: 账号被冻结 |
| api-service 卖家业务 | 21000-21999 | 21001: Key 格式无效, 21002: 额度不足以上架 |
| api-service 买家业务 | 22000-22999 | 22001: 商品已下架, 22002: 购买数量超过库存 |
| api-service 积分 | 23000-23999 | 23001: 积分余额不足, 23002: 充值金额无效 |
| billing-service 计量 | 30000-30999 | 30001: 平台模型不存在, 30002: 计费规则未配置 |
| billing-service Escrow | 31000-31999 | 31001: Escrow 记录不存在, 31002: 重复结算 |
| admin-service | 40000-40999 | 40001: 非管理员账号, 40002: 配置项不存在 |
| proxy-gateway | 50000-50999 | 50001: API Key 无效, 50002: 额度已耗尽, 50003: 目标平台不可用 |

**为什么这样设计？**

- **5 位数字 vs HTTP 状态码**：HTTP 状态码只有几十个，无法表达业务域的细粒度错误。前端需要根据具体错误码展示不同提示（如"余额不足"和"商品已下架"必须区分）。
- **层级分离**：全局错误码由框架/中间件统一抛出，业务错误码由 service 层抛出。维护者看到 1xxxx 知道是通用问题，看到 5xxxx 直接定位到网关。
- **预留空间**：每个服务分配 1000 个码，足够 V0.1-V1.0 阶段使用。

### 4.5 接口文档

- 所有 Python FastAPI 服务自动生成交互式文档：`/docs`（Swagger UI）、`/redoc`（ReDoc）。
- 对外接口（供买家调用的代理 API）需要额外维护 Markdown 文档，放在 `docs/api/` 目录。
- 每次接口变更后，由开发者手动更新 `docs/api/` 中的对应文档。

## 五、环境变量管理规范

### 5.1 环境分离策略

| 环境 | 用途 | 部署方式 | 配置文件 |
|------|------|----------|----------|
| **dev** | 本地开发 | 中间件 Docker + 前后端本地进程 | `.env.dev` |
| **test** | 测试/预览 | 全 Docker Compose 部署 | `.env.test` |
| **prod** | 生产环境 | 全 Docker Compose 部署 | `.env.prod` |

### 5.2 环境变量文件层级

采用 **三层配置叠加** 模型，优先级递增：

```
1. 系统默认值（代码中的 default）     ← 最低优先级
2. 环境变量文件（.env.{env}）          ← 中间优先级
3. 本地覆盖（.env.local, export）      ← 最高优先级
```

**执行规则**：

- `.env.example` 提交到 Git，包含所有配置项的注释说明和脱敏示例值。
- `.env.dev` / `.env.test` / `.env.prod` **不提交到 Git**，由开发者本地维护或通过安全渠道分发。
- 本地开发时如需临时覆盖某个值，可创建 `.env.local`（gitignore），或在 shell 中 `export`。

### 5.3 敏感信息管理

| 信息类型 | 管理方式 | 说明 |
|----------|----------|------|
| **数据库密码** | 环境变量 | `POSTGRES_PASSWORD` 通过 `.env` 注入 |
| **JWT 密钥** | 环境变量 | `SECRET_KEY` 通过 `.env` 注入 |
| **目标平台 API Key** | 数据库加密存储 | 卖家录入的原始 Key 经 AES 加密后存入 DB |
| **内部通信 Token** | 环境变量 | `INTERNAL_API_TOKEN` 用于服务间简单鉴权 |
| **支付相关密钥** | 环境变量 | 暂不接入真实支付，V0.1 使用模拟充值 |

**为什么 V0.1 不用 Docker Secrets？**

- Docker Secrets 需要 Swarm 模式，本地开发和单机部署开启 Swarm 增加复杂度。
- 当前阶段没有真正的支付密钥需要保护（使用模拟充值）。
- **扩展路径**：V0.3 引入 K8s 后，自然过渡到 K8s Secret 管理。

```makefile
# ========== 本地开发 ==========
dev:
	@echo "🚀 启动本地开发环境..."

	@sleep 3
	# 3. 执行数据库初始化
	@bash scripts/db/init-local.sh
	# 4. 并行启动各服务（新开终端/后台）
	@echo "请在多个终端中分别执行:"
	@echo "  make dev-gateway"
	@echo "  make dev-api"
	@echo "  make dev-billing"
	@echo "  make dev-admin"
	@echo "  make dev-frontend"

dev-gateway:
	cd services/proxy-gateway && go run cmd/gateway/main.go

dev-api:
	cd services/api-service && uvicorn app.main:app --reload --port 8000

dev-billing:
	cd services/billing-service && uvicorn app.main:app --reload --port 8001

dev-admin:
	cd services/admin-service && uvicorn app.main:app --reload --port 8002

dev-frontend:
	cd frontend && npm run dev

# ========== 构建 ==========
build:
	@echo "🔨 构建所有服务镜像..."
	docker-compose -f docker-compose.yml build

build-gateway:
	cd services/proxy-gateway && docker build -t tokenmarket/gateway:latest .

build-api:
	cd services/api-service && docker build -t tokenmarket/api:latest .

# ========== 测试环境部署 ==========
deploy-test:
	@echo "🧪 部署到测试环境..."
	# 前置条件检查
	@test -f .env.test || (echo "❌ .env.test 不存在" && exit 1)
	# 复制配置并启动
	cp .env.test .env
	docker-compose -f docker-compose.test.yml down
	docker-compose -f docker-compose.test.yml up -d --build
	@echo "✅ 测试环境部署完成"

# ========== 生产环境部署 ==========
deploy-prod:
	@echo "🚀 部署到生产环境..."
	@test -f .env.prod || (echo "❌ .env.prod 不存在" && exit 1)

	@read -p "⚠️  确认部署到生产环境? [y/N] " confirm && [ $$confirm = "y" ] || exit 1
	cp .env.prod .env
	docker-compose -f docker-compose.prod.yml down
	docker-compose -f docker-compose.prod.yml up -d --build
	@echo "✅ 生产环境部署完成"

# ========== 测试 ==========
test:
	@echo "🧪 运行测试..."
	cd services/api-service && pytest -v
	cd services/billing-service && pytest -v
	cd services/admin-service && pytest -v

test-gateway:
	cd services/proxy-gateway && go test ./...

# ========== 代码检查 ==========
lint:
	@echo "🔍 代码检查..."
	cd services/proxy-gateway && golangci-lint run
	cd services/api-service && black --check . && isort --check-only .
	cd services/billing-service && black --check . && isort --check-only .
	cd frontend && npx tsc --noEmit && npx eslint src/

# ========== 数据库迁移 ==========
migrate-up:
	cd services/api-service && alembic upgrade head

migrate-down:
	cd services/api-service && alembic downgrade -1

migrate-create:
	@read -p "迁移名称: " name; \
	cd services/api-service && alembic revision --autogenerate -m "$$name"

# ========== 清理 ==========
clean:
	@echo "🧹 清理 Docker 资源..."
	docker-compose -f docker-compose.yml down -v
	docker system prune -f
```

### 6.5 Git 工作流

仓库采用 **双长生命周期分支**，把测试部署线与生产发布线分开：

```
master        ←── 生产分支（始终可发布；生产部署的唯一代码源）
  ▲
  │  评审通过后的晋升 PR（test 验证后）
  │
master-dev    ←── 测试环境部署分支（集成与预发验证）
  ▲
  ├── feature/xxx  ←── 功能分支，开发完成后 PR 到 master-dev
  ├── fix/xxx      ←── 修复分支 → master-dev
  └── hotfix/xxx   ←── 紧急修复可直打 master，事后必须回并 master-dev
```

| 分支 | 角色 | 部署关系 |
|------|------|----------|
| `master` | 生产分支 | 对应生产环境发布线 |
| `master-dev` | 测试环境部署分支 | 对应测试环境发布线 |
| `feature/*` / `fix/*` | 短生命周期开发分支 | 不直接部署环境 |

**环境选择与分支的关系**：

- 分支只标记 **哪条代码线** 进入测试或生产。
- `make migrate` 及未来部署脚本仍必须显式传 `mode=local|test|prod`；**禁止**根据当前 Git 分支名推断环境（见 `environment-mode` 契约）。
- 未来 CD 可在 `master-dev` / `master` 的 push 上调度任务，但任务内仍须命令行传入对应 `mode=`（生产另加审批）。

**提交规范**（遵循 Conventional Commits）：

```
feat: 新功能
fix: 修复 bug
docs: 文档更新
style: 代码格式（不影响功能）
refactor: 重构
test: 测试相关
chore: 构建/工具链
```

**为什么是 master + master-dev？**

- 测试环境与生产使用独立部署线，避免「合进默认分支即上生产」。
- 功能先在 `master-dev` 集成并部署测试，再晋升 `master` 发布生产。
- 不引入完整 Git Flow 的 `develop`/`release`/`hotfix` 多重长分支；`hotfix/*` 仅作短生命周期紧急修复。

### 6.6 迭代节奏

| 阶段 | 周期 | 产出 |
|------|------|------|
| **V0.1 原型** | 2-3 周 | 核心链路跑通：卖家上架 → 买家购买 → API 代理调用 → 计量扣费 |

3. 晚：本地测试 → 提交代码 → 部署测试环境验证

### B. 单人开发效率优化

1. **代码生成**：使用 `scripts/codegen/generate-models.sh` 从数据库 schema 自动生成 Pydantic 模型和前端 TypeScript 类型，减少重复劳动。
2. **API 客户端生成**：后端变更接口后，运行 `scripts/codegen/generate-api-client.sh` 自动生成前端 API 调用代码。
3. **统一日志格式**：所有服务输出 JSON 格式日志，本地开发时通过 `make dev` 统一收集到终端，方便排查。
4. **一键重置**：`make clean && make dev` 可在 30 秒内重置本地环境到干净状态。
