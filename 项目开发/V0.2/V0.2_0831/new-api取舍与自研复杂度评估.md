# new-api 取舍与自研复杂度评估

## 1. 结论

V0.2 **不直接采用 new-api 作为买家端分配 API，也不把它放在 TokenMarket Gateway 的关键请求链路中**。可将其作为协议覆盖、厂商异常和运维界面的参考实现；若需要比较，使用隔离实验和黑盒合同测试，不复制其用户、渠道、充值、路由或计费领域模型。

该结论并非因为自研简单。三协议稳定数据面、长连接、文件/异步亲和、路由和准确结算属于 V0.2 最高复杂度工作；但 new-api 主要节省的是通用网关的初始接入，而 TokenMarket 仍必须重做决定产品正确性的 Project、供给、专享、路由、账本和审计部分，最终形成双重控制面和更难验证的语义边界。

## 2. 不直接采用的原因

new-api 官方定位是统一 AI 网关与用量管理系统，具备多渠道、加权路由、自动故障转移、成本管理和多协议格式转换能力；其仓库还包含用户、额度/充值和管理界面。这些能力本身有价值，但与 V0.2 已确认约束存在结构性冲突：

| V0.2 必须成立 | new-api 直接接入带来的冲突 |
|---|---|
| 同协议原生透传，禁止跨协议转换 | 核心卖点包含 OpenAI/Claude/Gemini 格式互转，增加字段或工具语义被转换的风险 |
| Project 整体 shared/dedicated 且模式不可改 | channel/令牌模型不能直接表达 TokenMarket 的 Project/Binding/Connection 不变量 |
| 专享故障关闭，必须买家确认人工更换 | 自动重试/故障转移语义可能把请求送到其他渠道 |
| 硬过滤后按健康、延迟、容量、价格综合评分 | 加权随机/渠道路由不能直接满足版本化、可重放的四因素决策 |
| reported cost 优先、否则多维 usage 费率、不可变账本 | 内部额度/计费不能替代 TokenMarket 的 reservation、双边分录、未决、对账和冲正 |
| 一个控制面和完整审计事实 | 引入第二套用户、Key、渠道、余额和管理员状态，容易发生双写与事实源冲突 |

此外，官方仓库采用 AGPL-3.0，并声明额外的界面署名/链接要求。任何复制、修改、网络部署或打包方案都必须先由法律/合规确认义务；这不是技术团队可以忽略的集成细节。参考：[new-api 官方仓库与许可说明](https://github.com/QuantumNous/new-api)、[官方项目介绍](https://github.com/QuantumNous/new-api-docs-v1/blob/main/content/docs/en/guide/wiki/basic-concepts/project-introduction.mdx)。

## 3. 自研复杂度衡量

以下为进入 Spec 计划前的量级评估，不是排期承诺。假设团队熟悉现有 Go/FastAPI/React 架构，三厂商都有可测试账号，且多人可并行：

| 工作块 | 复杂度 | 主要难点 | 对应 SF |
|---|---|---|---|
| 透明代理与目录 | XL | 未知字段、原生错误、版本、控制面阻断 | SF01、SF18 |
| 三厂商全稳定数据面 | XXL | 端点数量、工具/多模态、真实差分测试 | SF19–SF21 |
| SSE/WebSocket/文件/异步 | XL | 背压、取消、资源亲和、节点切换 | SF22 |
| 共享/专享路由 | XL | 原子容量、硬过滤、评分重放、故障关闭 | SF23–SF25 |
| 用量、价格与账本 | XXL | 厂商差异、精度、幂等、迟到事件、对账 | SF26–SF29 |

仅上述数据面与交易核心，合理量级约为 **24–40 工程人周**；完整 V0.2 还包括架构、身份、UI、后台、安全、压测和发布，需在各 SF 形成 plan 后重新估算。最大不确定性是“冻结日稳定端点”的实际数量、厂商测试权限、Realtime/异步资源行为和 reported cost 可获得性。

直接 fork/嵌入 new-api 可能在数周内形成多厂商演示，但为了满足 TokenMarket 不变量，仍需：关闭转换和自动切换、替换路由、重建身份/Project/Connection 映射、旁路其余额并接入本项目账本、补齐事件/审计和证明所有路径无语义改写。其改造与回归量预计仍为 **L–XXL**，且增加上游升级合并、双重可观测和许可证成本。因此它不是低成本捷径。

## 4. 允许借鉴的范围

- 厂商端点和模型覆盖线索，用来反查官方文档，不作为发布事实源。
- 厂商错误、限流、usage 字段和边缘案例列表，用来扩充 TokenMarket fixture。
- Realtime、流式和多媒体处理的工程思路，经独立安全/许可评审后重新实现。
- 管理页面的信息组织参考，不复用其充值、渠道、余额和身份逻辑。

## 5. 重新评估触发条件

只有同时出现以下情况才重新考虑引入：组件能以独立库方式提供原生同协议传输、可完全禁用转换/路由/计费/身份、许可证经批准、合同测试证明字节/事件语义不变，并且总拥有成本低于维护 TokenMarket 适配器。重新评估也不得改变 Project、专享失败关闭和不可变账本规则。
