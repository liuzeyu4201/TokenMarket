## Clarifications

### Session 2026-07-13

- Q: SF01 完成时，尚无业务功能的必需组件应达到什么状态？ → A: 所有必需组件具备最小可构建、可检查、含真实冒烟测试的骨架；`make fmt/lint/test/build` 全部可通过。
- Q: SF01 是否必须包含实际可执行的持续集成工作流？ → A: 必须交付持续集成工作流；提交或合并请求触发根级质量入口，任一必需检查失败即阻断合并。
- Q: 当工作区存在未提交的源码改动时，`make fmt` 应如何处理？ → A: 正常原地格式化这些文件；允许产生格式差异，但不得重置、删除或改变格式化范围之外的内容。
- Q: 未显式指定目标环境时，`make migrate` 应如何选择数据库？ → A: 默认仅使用 `mode=local`；迁移和部署脚本通过 `mode=local|test|prod` 切换，测试和生产必须显式指定，生产还需额外审批或确认。
- Q: 当 SF01 已完成但 SF02 尚未实现时，`make dev` 和 `make dev-down` 应处于什么状态？ → A: 命令存在且帮助完整，但明确报告“依赖 SF02 尚未就绪”、无副作用并返回失败；SF02 完成后替换为真实生命周期。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 从仓库根目录完成日常工程动作 (Priority: P1)

作为 TokenMarket 开发者，我希望通过仓库根目录的一组稳定命令完成环境启动与停止、格式化、检查、测试、构建和数据库迁移，以便不必记忆或拼接各组件的私有命令，并能立即判断整个动作是否成功。

**Why this priority**: 后续所有业务功能都会依赖同一套工程入口；如果入口缺失、语义不一致或静默跳过失败，开发结果将无法稳定复现，也无法形成可信的持续集成证据。

**Independent Test**: 在一份全新检出的仓库中，仅根据根目录帮助执行每个标准动作；验证命令能覆盖所有适用组件、报告明确结果，并在任一必需步骤失败时返回整体失败。

**Acceptance Scenarios**:

1. **Given** 开发者位于仓库根目录且所需系统工具已安装，**When** 查看工程帮助，**Then** 能看到 `dev`、`dev-down`、`fmt`、`lint`、`test`、`build` 和 `migrate` 七个公开标准动作，以及 `bootstrap`、`type-check` 等稳定支撑动作的用途、前置条件、副作用与常见失败处理。
2. **Given** 所有适用组件均满足检查条件，**When** 开发者执行任一标准动作，**Then** 该动作覆盖所有适用组件并以成功状态结束，同时逐项显示实际执行结果。
3. **Given** 某个适用组件的必需步骤失败，**When** 执行根目录动作，**Then** 整体以失败状态结束，并指出失败的组件、动作和可安全重试的下一步。
4. **Given** 工程基线被声明为完成，**When** 执行格式化、检查、测试和构建，**Then** 每个必需组件都有最小可验证骨架并执行真实步骤；任一组件未初始化时整体失败，不把未执行的检查计为通过。
5. **Given** SF01 已完成但 SF02 尚未实现，**When** 开发者执行 `make dev` 或 `make dev-down`，**Then** 命令不产生副作用，明确报告“依赖 SF02 尚未就绪”并返回失败；该预期失败不阻止 SF01 按自身范围验收。

### User Story 2 - 安全地准备本地配置 (Priority: P1)

作为首次参与项目的开发者，我希望从一份完整、安全的配置定义准备本地环境，同时确保真实密码、令牌、提供商 Key 和生产数据不会被提交或输出。

**Why this priority**: TokenMarket 后续会处理第三方高价值凭证；工程基线若允许真实秘密进入版本控制或日志，将在任何业务功能开始前形成不可接受的泄露风险。

**Independent Test**: 按开发文档从配置示例创建本地配置，检查所有必需项均可发现；随后执行版本控制与敏感信息扫描，验证真实配置文件被忽略，示例和命令输出不包含可用秘密。

**Acceptance Scenarios**:

1. **Given** 开发者首次检出仓库，**When** 阅读配置示例，**Then** 每个基线配置项都有用途、是否必需、允许环境和安全占位值说明。
2. **Given** 开发者创建包含本地真实值的环境配置，**When** 检查待提交文件，**Then** 该文件不会进入版本控制范围，只有安全配置定义可被提交。
3. **Given** 必需配置缺失或格式非法，**When** 执行依赖该配置的标准动作，**Then** 工作流在产生持久副作用前失败，并只显示变量名称和修复指引，不显示已有值。
4. **Given** 示例或文档中意外加入疑似凭证，**When** 执行标准检查，**Then** 检查失败并定位文件，不允许把该结果计为工程基线通过。

### User Story 3 - 在明确的组件边界内开始开发 (Priority: P2)

作为开发者或评审者，我希望仓库目录直接表达代理流量、领域服务、前端、共享契约、基础设施和运维资产的所有权，以便新增功能时能把代码、测试、迁移和契约放在唯一正确的位置。

**Why this priority**: 清晰边界可以减少跨服务读取内部实现、重复定义接口和把业务规则放进错误组件的风险，并为独立构建与发布保留空间。

**Independent Test**: 对仓库执行结构检查，验证必需组件目录、职责说明、测试根目录和版本化契约区均存在；加入一组故意放错位置的样例后，检查应准确失败。

**Acceptance Scenarios**:

1. **Given** 工程基线已建立，**When** 开发者寻找代理网关、三个领域服务、单一前端、共享契约、基础设施或运维资产，**Then** 每类资产都有唯一约定目录和清晰职责说明。
2. **Given** 团队准备新增跨组件 HTTP 或事件契约，**When** 开始消费者实现，**Then** 版本化契约已先被放入共享契约区，并标明所有者、版本和兼容规则。
3. **Given** 新文件违反组件边界或测试落在错误位置，**When** 执行结构或静态检查，**Then** 检查失败并指出违反的边界规则。
4. **Given** 提议新增服务、数据存储、协议或跨服务依赖，**When** 进入实现计划，**Then** 变更具有说明所有权、失败模式、迁移与回退的决策记录，否则不得作为基线的一部分继续。

### User Story 4 - 在本地与持续集成中获得相同结论 (Priority: P2)

作为变更提交者，我希望本地和持续集成使用相同的根目录动作与质量门禁，以便本地通过的证据在评审环境中仍然有效，并能从失败后直接重试而不需要清理未知状态。

**Why this priority**: 两套不同工作流会导致“本地通过、集成失败”或反向漏检；可重复执行与一致退出语义是可信交付的基础。

**Independent Test**: 对同一提交分别在本地和隔离的集成环境执行标准动作，比较动作清单、结果和工作区差异；注入中途失败后修复原因并直接重试，验证最终结论一致。

**Acceptance Scenarios**:

1. **Given** 开发者创建或更新合并请求，**When** 持续集成开始验证该提交，**Then** 工作流调用与本地相同的根目录入口、覆盖相同适用组件并采用相同通过标准；任一必需检查失败时合并被阻断。
2. **Given** 格式化、检查、测试或构建中途失败，**When** 开发者修复原因并重新执行，**Then** 无需手工删除未知状态即可得到与全新环境相同的结果。
3. **Given** 工作区已有用户未提交源码改动，**When** 执行 `make fmt`，**Then** 工作流可在声明的格式化范围内原地规范化文件，但不会重置、删除或改变格式化范围之外的内容；执行其他非破坏性标准动作时不会改写这些源码改动。
4. **Given** 工作流需要执行迁移或部署相关动作，**When** 开发者省略 `mode`，**Then** 动作只使用 `local`；`test` 或 `prod` 必须通过 `mode=test|prod` 显式选择，`prod` 还须在连接或修改生产资源前通过额外审批或确认。

### Edge Cases

- 开发者从包含空格或中文字符的绝对路径执行命令。
- 支持的工具链未安装、版本过低，或依赖锁文件缺失。
- 一个组件已初始化但没有任何测试，另一个约定组件尚未初始化。
- 同一标准动作被连续执行，或上一次执行在中途被终止。
- 工作区包含未提交文件、未跟踪文件或由用户创建的本地环境配置。
- 配置变量存在但为空、类型错误、使用生产环境标记，或包含看似可用的默认秘密。
- 共享契约发生破坏性修改但版本号与兼容说明未更新。
- 数据库迁移存在多个所有者、顺序不明确、回退说明缺失或目标环境不可确认。
- 命令输出终端不支持颜色、Unicode 图标或交互输入。
- 下游本地环境规格尚未实现，导致 `dev` 或 `dev-down` 无法完成真实依赖生命周期。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 仓库 MUST 提供并保留以下唯一组件边界：`services/proxy-gateway/`、`services/api-service/`、`services/billing-service/`、`services/admin-service/`、`frontend/`、`shared/`、`infra/` 和 `ops/`。
- **FR-002**: 每个组件边界 MUST 具有可发现的职责、所有者、允许依赖方向、构建入口和测试根目录说明；组件之间不得读取彼此的内部实现或持久化数据。
- **FR-003**: 仓库根目录 MUST 提供 `make dev`、`make dev-down`、`make test`、`make lint`、`make fmt`、`make build` 和 `make migrate` 七个稳定公开入口，作为开发者和持续集成的公开工程契约；同时 MUST 提供稳定的 `make bootstrap` 和 `make type-check` 支撑入口，且支撑入口不得改变七个公开动作的名称或语义。
- **FR-004**: 根目录 MUST 提供无需执行有副作用动作即可查看的帮助；帮助 MUST 说明每个公开入口和稳定支撑入口的用途、前置条件、适用组件、是否改变状态和常见恢复方式。
- **FR-005**: 每个聚合入口 MUST 明确列出并执行所有适用组件步骤；任一必需步骤失败时，聚合入口 MUST 返回失败状态。
- **FR-006**: SF01 完成时，每个必需组件 MUST 具备最小可构建、可检查且含真实冒烟测试的骨架，使 `make fmt`、`make lint`、`make test` 和 `make build` 均可执行真实步骤并通过；未初始化、未配置或使用空操作的组件 MUST 导致对应聚合入口失败。
- **FR-007**: 根工作流 MUST 在执行组件动作前验证所需系统工具是否存在且版本受支持；验证失败时 MUST 在产生持久副作用前停止。`make bootstrap` MUST 只使用已提交锁文件准备项目依赖，不得安装、升级或替换系统工具链，且重复执行不得改变锁文件。
- **FR-008**: `make dev` 与 `make dev-down` MUST 从 SF01 起作为本地依赖生命周期的稳定入口；在 SF02 尚未实现时，两者 MUST 无副作用地返回失败并明确报告“依赖 SF02 尚未就绪”，该状态属于 SF01 的合格过渡态；SF02 完成后，两者 MUST 由真实生命周期替换，且实际依赖集合、健康标准、持久化与停止语义不得在多个入口中重复定义。
- **FR-009**: 普通 `make dev-down` MUST 被定义为非破坏性停止；任何数据卷、缓存或构建产物的破坏性清理 MUST 使用独立动作并要求明确确认。
- **FR-010**: `make test` MUST 汇总所有适用组件的自动化测试，并对没有执行任何测试的适用组件给出不可忽略的结果。
- **FR-011**: `make lint` MUST 汇总所有适用组件的静态分析、类型检查与边界检查；`make type-check` MUST 提供相同类型检查集合的稳定独立入口；任何必需检查失败时整体 MUST 失败。
- **FR-012**: `make fmt` MUST 在声明的格式化范围内原地处理文件，包括已有未提交改动的源码；它可以产生纯格式差异，但 MUST NOT 重置、删除或改变格式化范围之外的内容，且连续两次执行 MUST 不产生额外差异。
- **FR-013**: `make build` MUST 对所有可交付组件执行可复现构建，并在失败时指明组件；构建不得依赖未声明的本地状态。
- **FR-014**: `make migrate` MUST 只执行已评审的迁移，按已声明的数据所有者和顺序运行；省略环境参数时 MUST 仅使用 `mode=local`，`mode=test` 与 `mode=prod` MUST 显式提供，且生产迁移 MUST 在连接或修改生产资源前通过额外审批或确认；应用启动不得替代该入口隐式改变生产数据结构。
- **FR-015**: 仓库 MUST 提交完整的 `.env.example` 或等价配置定义，只包含不可用的安全占位符，并说明每个配置项的用途、环境范围、是否必需和敏感级别。
- **FR-016**: 仓库 MUST 忽略 `.env`、`.env.dev`、`.env.test`、`.env.prod`、`.env.local` 及其他包含真实环境值的文件，同时允许安全配置定义被版本控制追踪。
- **FR-017**: 根工作流和文档 MUST NOT 输出、复制到构建产物或提交密码、访问令牌、提供商 API Key、加密密钥、生产地址或生产数据。
- **FR-018**: 每个组件和仓库工作流工具 MUST 声明并约束其工具链版本与直接依赖版本；适用的依赖锁文件 MUST 被提交，本地与持续集成 MUST 通过 `make bootstrap` 使用相同约束，且依赖准备不得重写锁文件或静默升级版本。
- **FR-019**: 跨组件 HTTP、事件或共享数据契约 MUST 在消费者实现前放入 `shared/` 的版本化位置，并包含所有者、兼容性和弃用规则。
- **FR-020**: 根 README 或等价开发文档 MUST 提供从检出仓库、验证工具链、准备本地配置到首次完成标准检查的最短路径，并链接各组件的详细说明。
- **FR-021**: 当现有根入口可以承载一个动作时，新增组件 MUST 扩展该入口；功能重复的一次性脚本不得成为新的公开工作流。
- **FR-022**: 工作流 MUST 正确处理包含空格或非 ASCII 字符的仓库路径，不得假定开发者使用固定绝对路径。
- **FR-023**: 除 `make fmt` 对声明范围内内容进行格式规范化外，非破坏性标准动作 MUST 保留所有用户未提交改动和未跟踪文件；任何标准动作均不得自动重置、删除或清理工作区，也不得改写其声明范围之外的内容。
- **FR-024**: 新增服务、数据存储、协议、共享抽象或跨服务依赖 MUST 在进入实现前具有经评审的架构决策记录，并说明所有权、失败模式、运维成本、迁移和回退。
- **FR-025**: SF01 MUST 交付实际可执行的持续集成工作流，在合并请求创建或更新以及主分支提交时通过根级入口执行锁定依赖准备、格式、类型与静态检查、测试、契约验证、隔离数据库迁移往返、敏感信息扫描和构建门禁；任一必需门禁失败 MUST 阻断合并或把主分支提交标记为失败。
- **FR-026**: 所有迁移和部署脚本命令 MUST 使用唯一的 `mode=local|test|prod` 环境选择契约；省略时 MUST 默认 `local`，非法值 MUST 在连接任何目标资源前失败，且不得通过当前 shell、配置文件名或残留变量隐式升级到 `test` 或 `prod`。

### Engineering Requirements *(mandatory)*

- **ER-001 — Contracts**: 公开动作名称、退出状态、副作用、适用组件和帮助文本属于开发者契约；语义变更必须同步本地文档与持续集成，并保留兼容迁移说明。
- **ER-002 — Security & Privacy**: 工程检查必须覆盖敏感信息与危险配置；秘密只可通过被忽略的环境配置或获批秘密来源注入，日志、错误、测试夹具和构建产物不得含真实秘密，生产必需安全配置缺失时必须失败关闭。
- **ER-003 — Data Integrity**: 数据结构变更只能经评审迁移入口执行；迁移顺序、所有者、向前兼容和回退方式必须明确，重复执行或失败重试不得造成重复状态变更，应用启动不得静默修改生产结构。
- **ER-004 — Performance & Capacity**: 在受支持的普通开发环境中，帮助应在 2 秒内可用，缺失工具或非法配置应在 5 秒内被发现；增量动作不得在每次执行时无条件重新安装所有依赖，具体完整测试与构建时长基线在计划阶段记录。
- **ER-005 — Reliability**: 所有标准动作必须可重复执行；中途失败或进程中断后，开发者修复原因即可直接重试，结果必须与干净环境一致，且只有已证明幂等的步骤可被自动重试。
- **ER-006 — Observability**: 每个标准动作必须以可解析且适合人阅读的方式报告动作、组件、开始、结果、耗时和安全错误摘要；任何输出均不得显示环境变量值或凭证。
- **ER-007 — Accessibility**: 本功能无图形界面；帮助和状态必须可由纯文本终端与屏幕阅读器理解，不得只依赖颜色、图标或动画表达成功、警告和失败。

### Failure and Recovery Scenarios *(mandatory)*

1. **Given** 工具链缺失、版本不支持或配置不合法，**When** 开发者执行标准动作，**Then** 工作流在修改持久状态前失败，指出工具或变量名称和支持范围，修复后可直接重试。
2. **Given** 一个聚合动作已完成部分组件后在后续组件失败，**When** 开发者重新执行该动作，**Then** 已完成步骤可被安全复用或重新执行，不会因上次半成品产生错误成功、重复迁移或无关文件漂移。
3. **Given** 本地与持续集成的组件清单或命令适配出现差异，**When** 执行工作流契约检查，**Then** 检查失败并列出缺失或多出的动作，直至两端恢复同一根入口。
4. **Given** 数据库迁移失败或发布需要回退，**When** 恢复开始，**Then** 恢复动作通过同一 `mode=local|test|prod` 契约明确目标环境，只使用已评审的 backout/回退说明恢复兼容状态，不编辑已应用迁移，也不由应用启动隐式修复。
5. **Given** 用户工作区包含未提交改动且动作中途失败，**When** 开发者检查工作区，**Then** 除 `make fmt` 已声明的纯格式修改和其他动作已声明的输出外，原有改动保持不变；恢复流程不得要求自动重置工作区。

### Key Entities *(include if feature involves data)*

- **Workflow Command Definition**: 根目录公开工程动作的定义，包含名称、目的、前置条件、适用组件、步骤、退出状态、副作用和恢复指引。根工作流文件是事实源，由仓库维护者所有；不含敏感数据，随版本控制永久保留，并通过评审记录语义变化。
- **Component Boundary**: 可独立检查和构建的仓库责任区，包含路径、职责、所有者、允许依赖、测试根目录和交付类型。架构规范与仓库结构共同构成事实源；边界变化必须经过评审和必要的架构决策记录。
- **Configuration Definition**: 可提交的配置元数据，包含变量名、用途、类型、必需性、环境范围、敏感级别和不可用占位值，不包含真实环境值。配置定义由各组件所有并在根示例聚合；真实值由开发者或运行环境持有，遵循各环境的删除与轮换策略。
- **Shared Contract Artifact**: 跨组件交互的版本化定义，包含所有者、版本、兼容规则和弃用信息。`shared/` 是发布事实源；变更必须可追溯到规格、测试和评审证据，不得以多份手工复制模型作为事实源。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 代表性新开发者中至少 90% 能在 15 分钟内，仅根据根目录帮助完成配置准备并启动第一次标准检查，无需搜索组件私有命令。
- **SC-002**: 七个标准动作及 `bootstrap`、`type-check` 两个稳定支撑动作在全部成功、单组件失败、组件未初始化、工具缺失、锁文件漂移和配置非法场景中的结果判定准确率达到 100%，不存在静默失败或空操作伪成功；连续两次 bootstrap 不修改锁文件或产生额外依赖解析差异。
- **SC-003**: 对同一提交连续两次执行格式化、检查、测试和构建后，第二次执行不会产生新的非预期版本控制差异，10 轮重复验证全部通过。
- **SC-004**: 100% 合并请求创建或更新及主分支提交都会触发持续集成；其公开动作、适用组件和质量门禁与本地匹配率达到 100%，且任一必需门禁失败都会阻断合并或把提交标记为失败。
- **SC-005**: 对包含真实配置文件、疑似凭证和危险默认值的验证样例，安全检查检出率达到 100%；正常配置示例保持零有效凭证和零误提交真实 `.env.*` 文件。
- **SC-006**: 结构验证对缺失必需目录、错误测试位置、越界依赖和未版本化共享契约的预置违规样例检出率达到 100%。
- **SC-007**: 在包含空格或中文字符的工作区路径中，七个标准动作的帮助与前置检查全部能够正常运行，且不会访问仓库外的同名路径。
- **SC-008**: 100% 会改变持久状态或删除数据的动作在帮助中明确标注影响和恢复方式；普通停止、检查和格式化动作不会触发破坏性清理。
- **SC-009**: 在不实现任何业务功能的全新工程基线上，所有必需组件均至少执行一项真实静态检查、一项真实冒烟测试和一次真实构建，根级格式化、检查、测试与构建四个动作全部通过。
- **SC-010**: 在包含预置未提交源码改动和未跟踪文件的验证工作区中，`make fmt` 对格式化范围内文件的处理成功率达到 100%，连续第二次执行零新增差异，且范围外内容、未跟踪文件和版本控制状态均不被重置或删除。
- **SC-011**: 环境选择测试中，省略 `mode` 的迁移或部署相关命令 100% 只选择本地环境，`mode=test` 与 `mode=prod` 100% 只选择对应环境，非法值和未获额外批准的生产动作 100% 在连接或修改目标资源前失败。
- **SC-012**: 在 SF02 未实现的基线验证中，`make dev` 与 `make dev-down` 100% 返回非零状态、输出唯一明确的 SF02 未就绪原因且不创建、停止、删除或修改任何本地依赖资源。

## Assumptions

- 目标用户是参与 TokenMarket 开发、评审和持续集成维护的工程人员，不是平台买家、卖家或管理员。
- 项目工程宪章高于周度 Spec、PRD 和各工程参考文档；“原型阶段”不构成弱化秘密保护、迁移安全或测试门禁的例外。
- 根目录工作流是唯一对开发者承诺的公开入口；组件内部命令可以存在，但只作为根工作流的受控实现细节。
- 开发者已安装项目声明的受支持系统工具链；系统工具的安装自动化不属于本功能，但检测和清晰提示属于本功能。`make bootstrap` 只准备锁文件约束的项目依赖，不负责安装 Go、Python、Node、Docker 或扫描器等系统工具。
- `make dev` 实际启动哪些本地依赖、如何判定健康以及停止时保留哪些数据由 SF02 或其后续有效规格负责；SF01 只建立不可分叉的根入口及无副作用的未就绪失败状态。因此，参考文档中 Kafka 是否属于 V0.1 强制依赖的差异不会扩大本功能范围。
- 本功能为每个必需组件建立可构建、可检查且含真实冒烟测试的最小骨架，但不要求任何买家、卖家、Key、代理、计量或监控业务能力已实现。
- 现有组件技术边界和版本基线来自工程宪章；替换技术、职责或增加跨服务依赖需要单独决策记录，不在本功能中默认批准。

## Scope

### In Scope

- Monorepo 必需组件的最小可构建、可检查、含真实冒烟测试的骨架与职责说明。
- 根目录标准工作流、稳定的锁定依赖准备与类型检查入口、帮助、退出语义、组件聚合和可重复执行规则。
- 迁移及未来部署脚本统一使用的 `mode=local|test|prod` 环境选择与生产确认契约。
- 安全配置示例、忽略规则、配置前置检查与敏感信息防护。
- 共享契约的版本化位置与所有权规则。
- 实际可执行的持续集成质量门禁、本地与持续集成的一致性验证、结构验证和开发者入门说明。

### Out of Scope

- PostgreSQL、Redis、Kafka、Grafana 或其他依赖的具体编排、健康检查和数据卷实现；这些由本地环境功能负责。
- 用户注册登录、提供商 Key 管理、代理请求、路由、计量、计费、结算、监控看板和任何业务接口。
- 前端页面或视觉设计。
- 云部署与生产发布自动化的具体实现、Kubernetes、真实生产配置和真实凭证分发；SF01 只定义这些脚本必须遵循的 `mode` 环境选择契约。
- 对现有技术栈、服务数量或领域所有权的重新设计。
