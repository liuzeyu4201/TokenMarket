# TokenMarket 产品迭代路线图

> **文档定位**：指导开发团队从V0.1内测到V3.0企业SaaS的完整产品演进计划
> **适用对象**：产品、研发、运营、管理层
> **更新周期**：每月Review，里程碑节点强制Review

---

## 1. 迭代总览

### 1.1 版本时间轴总览

| 阶段 | 版本 | 时间 | 核心主题 | 目标用户 | 接入平台数 | 关键验证假设 |
|------|------|------|----------|----------|------------|--------------|
| 内测期 | V0.1 | 第1个月 | 技术验证：核心路由+单平台 | 内部团队+技术KOL | 1 | 请求代理转发链路可用，延迟<500ms |
| 内测期 | V0.2 | 第2个月 | 封闭内测：双平台+基础交易 | 种子卖家+买家（各20人） | 2 | C2C撮合闭环跑通，Escrow资金流转安全 |
| MVP发布 | V1.0 | 第3个月 | MVP正式发布：双平台稳定交易 | 早期采纳者开发者 | 2 | 月GMV>5万元，撮合成功率>85% |
| 信任增长 | V1.1 | 第4-5个月 | 评价裂变+信任体系建设 | 个人开发者扩散 | 2 | NPS>40，邀请转化率>15% |
| 多平台扩展 | V1.2 | 第6-8个月 | 四平台覆盖+会员订阅 | 中型开发团队 | 4 | 月GMV>30万元，会员付费率>10% |
| 规模化 | V2.0 | 第9-12个月 | 国际平台+企业SaaS雏形 | 企业IT管理员 | 6 | 企业客户签约>5家，ARR>50万 |
| 企业升级 | V3.0 | 第12-18个月 | 企业SaaS完整版+开放平台 | 中大型企业 | 6+ | 企业收入占比>50%，月度续约率>90% |

### 1.2 三阶段战略映射

```
Plan A（C2C个人撮合，0–12个月）        Plan B（企业SaaS，12–24个月）       Plan C（开源聚合，24个月+）
        │                                      │                                 │
    V0.1 → V0.2 → V1.0 → V1.1 → V1.2 → V2.0 → V2.5 → V3.0 → V3.5 ───────→ 开源模型聚合层
        │                                      │                                 │
   [验证双边市场]                         [防御平台官方池化]                  [构建差异化壁垒]
```

## 2. V0.x 内测期（第1–2个月）

> **阶段目标**：验证技术可行性，跑通最小交易闭环，收集首批真实用户反馈
> **阶段预算**：约15万元（人力+云资源+测试额度采购）

### 2.1 V0.1 技术验证版（第1个月）

#### 功能清单

| 模块 | 功能点 | 优先级 | 说明 |
|------|--------|--------|------|
| 基础设施 | 请求代理网关 | P0 | 基于OpenAI-compatible API规范构建代理层 |
| 基础设施 | 火山方舟平台接入 | P0 | 支持Coding Plan额度调用，实现Key透传与用量透传 |
| 基础设施 | 健康检查机制 | P0 | 每分钟检测卖家Key可用性，异常自动摘除 |
| 基础设施 | 基础轮询路由 | P0 | 简单Round-Robin分发到可用卖家Key |
| 基础设施 | 用量计量服务 | P0 | 按Token数实时计量，记录输入/输出Token |
| 数据层 | 用户账户表 | P0 | 手机号注册，基础用户信息 |
| 数据层 | API Key管理表 | P0 | 卖家上传的Key加密存储（AES-256） |
| 数据层 | 用量日志表 | P0 | 每次请求的Token消耗、路由路径、耗时 |
| 监控 | 基础日志与告警 | P1 | 错误率>5%时触发告警 |

#### 成功指标（量化）

| 指标 | 目标值 | 测量方式 |
|------|--------|----------|
| 代理请求成功率 | >98% | 监控日志统计 |
| 平均请求延迟（P95） | <800ms | 网关埋点 |
| 火山方舟API兼容性 | 100%通过标准测试集 | 自动化测试 |
| 内部压测QPS | >100 | 负载测试 |

#### 风险点

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|----------|
| 火山方舟API限制或变更 | 中 | 高 | 提前阅读官方文档，预留适配层抽象接口 |
| Key泄露导致卖家额度被盗刷 | 低 | 高 | Key加密存储+IP白名单+异常用量熔断 |
| 高并发下路由性能瓶颈 | 中 | 中 | 使用Redis缓存状态，网关水平扩展 |

#### 里程碑交付物

- [ ] 代理网关代码仓库（含单元测试）
- [ ] 火山方舟兼容测试报告
- [ ] 内部压测报告
- [ ] 安全审计检查单（Key存储、传输加密）

#### 内测用户招募策略

**卖家侧招募（目标20人）**

1. **定向邀请**：从开发者社群（V2EX、掘金、GitHub中文圈）筛选有火山/智谱额度的活跃用户
2. **利益驱动**：内测期零平台抽成（100%收益归卖家），额外赠送100元充值金
3. **KOL合作**：邀请3-5位AI开发领域KOL体验并输出评测内容
4. **企业溢出**：联系已购买企业版Coding Plan但有剩余额度的中小团队

**买家侧招募（目标20人）**

1. **价格敏感型开发者**：在AI开发社群发布"85折用官方API"钩子
2. **学生群体**：通过高校计算机社团、AI Lab定向邀请
3. **现有卖家转化**：允许卖家同时作为买家消费（促进内部循环）
4. **竞品用户**：在Cursor/Trae用户群中推广"更低成本用同模型"

### 8.3 提前终止条件（Kill Switch）

以下任一条件触发时，需立即召开紧急战略会议，评估是否继续项目：

1. **政策风险**：任一目标平台明确禁止额度转让行为，且发出律师函或封禁账号
2. **市场消失**：火山/智谱等主流平台官方推出额度池化/共享功能，且价格低于本平台
3. **资金断裂**：连续3个月现金流为负，且融资未到位
4. **安全事件**：发生用户资金被盗、Key大规模泄露等严重安全事件
5. **团队溃散**：核心技术人员或创始人退出，且无替代方案

## 10. 风险与缓冲计划

### 10.1 平台方推出官方池化的应对（最高优先级）

**触发信号**：
- 火山/智谱官方发布额度共享/转让功能
- 官方推出「团队版」「企业共享池」等产品
- 官方价格下调至接近本平台卖家挂售价

**应对策略**：

| 阶段 | 应对措施 |
|------|----------|
| 预防（当前） | ①加速企业SaaS和数据分析能力建设，构建非价格型差异化<br>②与平台方建立商务联系，探索官方合作可能性（成为官方分销渠道） |
| 早期（官方公告但未上线） | ①评估官方功能与本平台的功能差距，针对性强化<br>②启动「平台不可取代」用户教育：多平台聚合、成本优化分析、跨平台管理 |
| 中期（官方已上线） | ①若官方价格有优势：转型为「官方渠道+第三方补充」的混合模式<br>②若官方功能有局限：聚焦官方不覆盖的场景（跨平台、开源模型、国际平台） |
| 后期（官方完全替代） | 全面转向Plan B企业SaaS + Plan C开源聚合，C2C撮合降级为流量入口 |

**缓冲时间窗口**：
- 国内平台（火山/智谱/ MiniMax/ Kimi）通常需要6-12个月从公告到产品成熟
- 利用此窗口快速建立企业客户粘性和开源模型能力

### 10.2 免费工具（Trae/MarsCode等）截流的应对

**威胁分析**：
- Trae（字节）、MarsCode（字节）、Cursor免费版等工具提供「免费/低价AI Coding」
- 可能分流对价格敏感的个人开发者买家

**应对策略**：

| 维度 | 应对措施 |
|------|----------|
| 定位差异 | 强调TokenMarket是「API层」服务，不是「IDE工具」——买家可用任何IDE，灵活性更高 |
| 客群上移 | 将重心从纯个人开发者转向「有自定义需求的专业开发者」和「企业团队」 |
| 生态合作 | 与IDE工具合作（如成为Cursor/VS Code插件的推荐API提供商），而非对抗 |
| 成本透明 | 提供「自建vs免费工具vsTokenMarket」的真实成本对比，证明对高频用户更划算 |

### 10.3 API封禁或条款变更的应对

**风险场景**：
- 平台方检测到异常API调用模式，封禁代理Key
- 平台方更新用户协议，明确禁止额度转让
- 平台方限制单Key的调用IP数或QPS

**应对策略**：

| 层级 | 措施 |
|------|------|
| 技术层 | ①代理请求行为模拟：模拟正常用户调用模式（请求间隔、User-Agent等）<br>②IP轮询池：建立住宅IP代理池，分散请求来源<br>③Key轮换策略：自动切换备用Key，降低单Key曝光度 |
| 商务层 | ①与平台方建立正式合作关系，获得API代理许可<br>②若平台方推出官方渠道，申请成为认证合作伙伴 |
| 法务层 | ①用户协议明确：平台仅提供技术服务，额度流转由用户自主决定<br>②准备合规预案，必要时限制特定平台的服务范围 |
| 战略层 | ①不过度依赖单一平台，保持多平台均衡分布<br>②开源模型（Plan C）作为终极兜底方案 |
