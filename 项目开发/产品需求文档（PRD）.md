## 2. 项目概述

### 2.1 产品定位

TokenMarket 是一个**AI Coding Plan 额度实时撮合与代理平台**，致力于解决国内主流 AI Coding Plan 平台（火山方舟、智谱GLM、Kimi、MiniMax、Claude Code、GPT 等）"固定订阅+硬停止"计费模式所导致的系统性资源浪费问题。平台通过构建**C2C实时撮合+技术代理隔离**的双层架构，为额度剩余者提供挂售变现渠道，为额度需求者提供按需低价的使用方案，同时为平台创造可持续的利差收入。

**一句话定位**：让 AI Coding Plan 的闲置额度流动起来，实现三方共赢。

### 2.2 核心价值主张

| 利益相关方 | 核心痛点 | TokenMarket 解决方案 | 价值主张 |
|-----------|---------|---------------------|----------|
| **卖家（额度剩余者）** | 月度订阅额度利用率仅 5%–15%，到期自动清零，无法累积或退款，造成资金浪费 | 一键接入 API Key，设置挂售折扣，闲置额度实时变现 | 让沉睡的额度产生价值，止损回血 |
| **买家（额度需求者）** | 月订阅费用高（¥40–¥469），但需求波动大，临时使用需承担完整订阅成本 | 按需购买平台代理Key，按实际使用量付费，价格低至官方 80% | 无需绑定订阅，随用随买，大幅降低 AI Coding 使用成本 |
| **平台（TokenMarket）** | — | 实时撮合交易，赚取 15% 左右利差，不囤积额度，不承担过期风险 | 轻资产撮合平台，纯技术驱动，可持续商业模式 |

### 2.4 成功指标（North Star Metric）

**北极星指标：月度撮合交易额（GMV，Gross Merchandise Volume）**

> 定义：平台上自然月内买家通过 TokenMarket 代理Key消费的总金额（以人民币计价，外币按当月平均汇率折算）。
> 为什么选它：GMV 同时反映了平台的市场规模（买家侧活跃度）、供给充足度（卖家侧挂售规模）和平台撮合效率（交易闭环能力），是唯一能够综合衡量平台健康度的核心指标。

**辅助指标体系（L1 Metrics）：**

| 指标类别 | 指标名称 | 计算公式/定义 | MVP目标 | 6个月目标 | 12个月目标 |
|----------|---------|-------------|---------|----------|-----------|
| 市场规模 | 月度GMV | 自然月买家消费总金额 | ¥50万 | ¥200万 | ¥1000万 |
| 供给侧 | 活跃卖家数 | 自然月有挂售且被消费的卖家数 | 200人 | 800人 | 3000人 |
| 需求侧 | 活跃买家数 | 自然月有消费行为的买家数 | 500人 | 2000人 | 10000人 |
| 效率 | 撮合成功率 | 买家请求成功被路由至可用卖家Key的比例 | ≥95% | ≥98% | ≥99.5% |
| 留存 | 卖家次月留存率 | 本月挂售且下月仍有挂售行为的卖家占比 | ≥60% | ≥70% | ≥75% |
| 留存 | 买家次月留存率 | 本月消费且下月仍有消费行为的买家占比 | ≥50% | ≥65% | ≥70% |
| 财务 | 平台毛利率 | 平台收入（利差）/ GMV | 12% | 14% | 15% |
| 体验 | API平均响应延迟 | 买家请求到收到首字节（TTFB）的中位数 | ≤800ms | ≤500ms | ≤300ms |
| 体验 | 月度故障时间 | 月度不可用分钟数 | ≤60min | ≤30min | ≤15min |

**L2 Metrics（细分指标，用于日常监控和诊断）：**
- 卖家注册转化率 = 访问卖家注册页 → 完成注册的比例
- 卖家挂售转化率 = 完成注册 → 完成首次挂售的比例
- 买家首充转化率 = 完成注册 → 完成首次充值的比例
- 单用户月均消费（ARPU）= 月度GMV / 活跃买家数
- 单卖家月均挂售额 = 月度卖家挂售总额 / 活跃卖家数
- 代理Key平均可用率 = 有可用额度的代理Key数 / 总激活代理Key数
- 健康检查失败率 = 健康检查失败次数 / 总健康检查次数
- 计费争议率 = 月度计费争议工单数 / 月度总交易笔数

## 3. 产品架构总览

### 3.1 系统架构图（文字描述）

TokenMarket 系统采用**四层代理链路 + 三层服务端**的架构设计，确保 API Key 安全隔离、请求智能路由、计费实时准确。

#### 3.1.1 四层代理链路（请求处理管道）

```
┌─────────────────────────────────────────────────────────────────┐
│  L1：API Key 接入层（Key Ingestion Layer）                       │
│  • 卖家通过 Web 端提交原始 API Key                                │
│  • AES-256-GCM 加密，密钥由 HSM（硬件安全模块）托管               │
│  • 支持平台：火山方舟、智谱GLM、MiniMax、Kimi、Claude、GPT        │
│  • 输出：加密存储的原始 Key，永不明文落盘                        │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│  L2：代理 Key 生成层（Proxy Key Generation Layer）              │
│  • 为每个买家/每个平台生成唯一 UUID v4 代理 Key                    │
│  • 建立"原始Key → 代理Key → 买家" 的三方映射关系表                 │
│  • 动态权限控制：可设置可用模型、可用额度上限、有效期             │
│  • 输出：平台代理Key，可像普通 API Key 一样被调用                  │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│  L3：智能路由层（Smart Routing Layer）                           │
│  • 负载均衡：根据卖家Key剩余额度、响应延迟、成功率选择最优路由       │
│  • 健康检查：每 30 秒检查一次卖家Key可用性（余额、权限、响应）      │
│  • 故障自动切换：单个卖家Key失败时，毫秒级切换至备用Key             │
│  • 速率限制：保护卖家Key不被过载，避免触发平台限流                  │
│  • 输出：路由决策 → 选定卖家原始Key → 转发请求                     │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│  L4：实时计量层（Real-time Metering Layer）                       │
│  • 流式日志采集：拦截请求/响应，记录完整调用上下文                  │
│  • Token 计数：按官方计费规则精确计算输入/输出 Token 数             │
│  • 计费引擎：实时累计消费金额，更新买家余额和卖家收益                │
│  • 对账系统：每小时生成卖家/买家/平台三方对账报告                  │
│  • 输出：计费流水、余额变更、对账报告                              │
└─────────────────────────────────────────────────────────────────┘
```

#### 3.1.2 三层服务端架构（Server-side Architecture）

```
┌─────────────────────────────────────────────────────────────────┐
│  接入层（Edge Layer）                                             │
│  • CDN + WAF：静态资源加速、DDoS防护、Bot检测                    │
│  • API Gateway：统一入口、限流、鉴权、TLS 1.3 终止                  │
│  • 负载均衡：Nginx / ALB，支持 WebSocket 长连接                    │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│  应用层（Application Layer）                                      │
│  • 用户服务：注册、登录、实名认证、权限管理                         │
│  • 卖家服务：Key管理、挂售设置、收益管理、状态监控                  │
│  • 买家服务：代理Key管理、充值、消费、账单查询                      │
│  • 路由服务：智能路由引擎、健康检查、故障切换                      │
│  • 计费服务：实时计量、余额管理、结算引擎、对账                     │
│  • 积分服务：TMP积分、会员等级、邀请裂变                            │
│  • 后台服务：用户管理、交易监控、风控、数据分析                     │
│  • 通知服务：站内信、邮件、Webhook（余额不足、收益到账等）           │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│  数据层（Data Layer）                                             │
│  • 关系数据库：PostgreSQL（主存储：用户、交易、订单、配置）          │
│  • 时序数据库：InfluxDB（API 调用量、延迟、错误率指标）              │
│  • 缓存：Redis（会话、路由状态、热Key、速率限制计数器）             │
│  • 消息队列：Kafka（计费流水、日志、异步任务）                      │
│  • 对象存储：MinIO/S3（审计日志、对账文件、备份）                   │
│  • HSM：Thales Luna 7（AES-256 密钥管理，原始Key解密）             │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 数据流图（文字描述）

#### 3.2.1 正常交易数据流（买家调用代理Key）

```
步骤1：买家发起请求
  买家 → 使用 TokenMarket 代理Key → 调用 API Gateway

步骤2：请求鉴权
  API Gateway → 检查代理Key有效性（Redis 缓存）→ 验证通过

步骤3：路由决策
  路由服务 → 查询可用卖家Key列表（剩余额度 > 0，健康状态 = UP）
         → 按加权算法选择最优卖家Key（权重：剩余额度40%、延迟30%、成功率30%）
         → 返回选定的卖家Key ID

步骤4：请求解密与转发
  L2代理层 → 根据代理Key ID 查询映射关系 → 获取加密原始Key ID
  L1接入层 → 向 HSM 发起解密请求 → 获取明文原始Key（内存中，不落盘）
         → 使用原始Key 向官方平台 API 发起请求

步骤5：响应流式返回
  官方平台 → 流式返回响应 → 代理层 → 买家（首字节到达）

步骤6：实时计量（并行）
  L4计量层 → 拦截请求/响应 → 解析 Token 使用量（输入 + 输出）
         → 按官方计费标准计算费用
         → 更新买家余额（扣减）
         → 更新卖家挂售额度（扣减）
         → 更新卖家待结算收益（增加）
         → 写入 Kafka 计费流水
         → 更新 InfluxDB 指标（延迟、Token数、状态码）

步骤7：Escrow 结算（每小时批处理）
  结算引擎 → 读取 Kafka 计费流水 → 汇总上一小时消费
         → 买家确认消费（无需操作，默认确认）
         → 卖家待结算收益 → 可提现收益（冻结期 24h 后释放）
         → 平台手续费 → 平台收入账户
```

#### 3.2.2 卖家挂售数据流

```
步骤1：卖家提交 API Key
  卖家 → 卖家端 Web 页面 → 选择平台（火山/智谱/…）→ 输入原始 API Key

步骤2：Key验证与加密
  系统 → 调用官方平台验证 API（验证 Key 有效性、剩余额度、可用模型）
       → 验证通过 → 调用 HSM 生成加密密钥 → AES-256-GCM 加密原始Key
       → 加密密文存储至 PostgreSQL（原始Key 明文立即从内存中清除）
       → 返回"Key 接入成功"

步骤3：挂售设置
  卖家 → 设置挂售额度上限（不超过Key剩余额度）→ 设置折扣率（60%–75%）
       → 设置有效期（可选，默认至额度用完或Key到期）→ 确认挂售

步骤4：代理Key生成（首次有买家使用时触发，或预生成）
  系统 → 为买家生成 UUID v4 代理Key → 建立映射关系
       → 代理Key可用状态 = ACTIVE
       → 纳入智能路由池
```

#### 3.2.3 提现数据流

```
步骤1：卖家发起提现
  卖家 → 查看可提现收益 → 选择提现方式（支付宝/微信/银行卡）→ 输入金额
       → 实名认证校验（未认证需先完成）→ 提交提现申请

步骤2：风控审核（自动/人工）
  系统 → 检查提现金额 ≤ 可提现余额 → 检查提现频率（每日限3次）
       → 检查账户风险等级（低/中/高）
       → 低风险：自动通过 → 进入支付队列
       → 中风险：延迟 2 小时 → 无异常自动通过
       → 高风险：人工审核 → 24h 内处理

步骤3：资金结算
  支付网关 → 处理提现 → 卖家收款 → 发送到账通知（站内信 + 邮件）
  系统 → 更新卖家账户余额 → 记录提现流水 → 写入审计日志
```

## 4. 功能模块详述

### 4.1 卖家端功能（Seller Portal）

#### 4.1.1 API Key 接入与管理

**功能描述：**  卖家通过安全通道将原始 API Key 接入 TokenMarket 平台。平台对 Key 进行验证、加密和隔离存储，确保卖家原始Key 永不暴露。卖家可以查看已接入的Key列表、管理Key状态（挂售中/暂停/已用完/已过期）。

### 4.3 平台核心功能（Platform Core）

#### 4.3.1 智能路由引擎

**功能描述：**  智能路由引擎是平台的核心技术组件，负责将买家的代理Key请求实时匹配到最优的卖家原始Key。路由决策基于多维度加权算法，确保高可用性、低延迟、公平分发。

**目标用户：**  平台系统（间接服务于买家和卖家）

**用户故事：**

> **故事1（买家）：** 我生成了一个代理Key后，希望每次调用都能成功，不需要关心后台是哪个卖家的Key在响应。即使某个卖家Key出问题了，我的调用也不应该中断。

> **故事2（卖家）：** 我希望我的Key能被公平地使用，而不是总是给某个大客户独占。如果我的Key性能更好，希望能被优先使用，这样我能卖出更多额度。

**Acceptance Criteria（验收标准）：**

| 编号 | 验收标准 | 优先级 | 验证方式 |
|------|---------|--------|----------|
| AC-3.1.1 | 路由引擎支持以下路由策略：加权轮询（Weighted Round-Robin）、最小连接数（Least Connections）、最低延迟（Lowest Latency）、智能综合（默认，加权评分：剩余额度40% + 响应延迟30% + 历史成功率20% + 卖家等级10%） | P0 | 压力测试 |
| AC-3.1.2 | 路由决策时间 ≤ 10ms（从请求到达网关到确定目标卖家Key）。在Redis缓存中维护可用卖家Key列表，命中缓存时决策时间 ≤ 5ms | P0 | 性能测试 |
| AC-3.1.3 | 当单个卖家Key请求失败（HTTP 429/500/502/503，或连接超时5秒）时，系统自动在 ≤ 100ms 内重试下一个可用Key。最多重试3次，3次均失败后向买家返回错误，错误信息包含"当前服务繁忙，请稍后重试" | P0 | 故障注入测试 |
| AC-3.1.4 | 健康检查每30秒执行一次，检查内容：调用官方平台余额查询（验证Key有效性）、发送一个测试请求（测量响应延迟）、检查剩余额度。检查结果更新至Redis，并标记Key状态（UP/DOWN/WARNING） | P0 | 功能测试 |
| AC-3.1.5 | 当卖家Key被标记为DOWN时，系统立即从路由池移除，同时尝试将该Key上的正在进行的请求平滑迁移至其他Key（仅适用于无状态流式请求的中断点续传，P2） | P0 | 功能测试 |
| AC-3.1.6 | 同一买家的连续请求在1分钟内优先路由到同一卖家Key（会话亲和性，Session Affinity），减少模型切换导致的上下文不一致问题。如该Key不可用，则打破亲和性 | P1 | 功能测试 |
| AC-3.1.7 | 支持紧急熔断：当某个官方平台整体出现大面积故障（如火山方舟API大面积429）时，系统自动将该平台所有Key暂时降级，优先路由至其他平台Key（如买家代理Key支持多平台备份时） | P1 | 故障注入测试 |
| AC-3.1.8 | 路由引擎支持A/B测试：可为特定流量比例（如5%）启用新的路由算法，对比效果后再全量上线 | P2 | 功能测试 |

**依赖关系：**  依赖Redis缓存集群；依赖官方平台API可用性；依赖健康检查服务。

**技术约束：**  路由决策必须是无状态的（支持水平扩展）；重试机制必须避免级联故障（指数退避）；同一Key的并发请求数不得超过官方平台限速的80%。

#### 4.3.3 Escrow 担保与结算

**功能描述：**  Escrow（第三方托管）机制确保买家消费的资金在交易完成前由平台托管，冻结期结束后才释放给卖家。该机制保护买家免受欺诈（如Key无效、额度虚报），同时保护卖家免受恶意退款。

**目标用户：**  平台系统（间接服务于买家和卖家）

**用户故事：**

> **故事1（买家）：** 我充了钱消费，如果卖家的Key实际上不能用（比如余额虚报），我希望能追回我的钱。

| 编号 | 验收标准 | 优先级 | 验证方式 |
|------|---------|--------|----------|
| AC-3.3.1 | 买家每次消费产生的费用，在买家账户中立即扣减，但对应卖家收益进入"待结算"状态（冻结），冻结期为24小时 | P0 | 功能测试 |

### 6.3 埋点实施要求

- **埋点 SDK**：前端使用 Web SDK（JavaScript），后端使用 Server SDK（Java/Go），确保全链路追踪。
- **数据上报**：采用异步上报，通过 Kafka 缓冲，避免影响主业务流程。上报失败时本地缓存，恢复后补发。
- **数据存储**：事件数据存储至 ClickHouse（分析型数据库），支持实时查询和离线分析。
- **隐私合规**：埋点数据不包含用户敏感信息（如原始Key、密码、身份证号），用户ID采用假名化处理。支持用户"拒绝追踪"选项（不影响核心功能使用）。
- **数据看板**：使用 Grafana / Metabase 搭建实时数据看板，运营团队可自助查询和分析。

| ASM-09 | 监管环境对C2C额度撮合持中性或支持态度，不视为非法金融活动或违规转租 | 监管假设 | 法务咨询、关注监管动态 | 高：如监管收紧，需申请相关牌照或调整商业模式 |
| ASM-10 | 核心开发团队能在3个月内完成MVP开发并上线，满足质量要求 | 执行假设 | 项目管理、里程碑评审 | 中：如延期，需缩减MVP范围，优先P0功能 |
