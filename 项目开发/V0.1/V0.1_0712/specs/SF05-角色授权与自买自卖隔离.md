# Feature Specification: SF05 角色授权与自买自卖隔离

**Feature ID**: `SF05`  
**Short Name**: `role-access-isolation`  
**Created**: 2026-07-13  
**Status**: Draft  
**Source**: 周度 Spec F02、PRD 角色权限矩阵、宪章授权要求

## 目标与价值

在服务端统一执行买家、卖家和双角色账户的最小权限规则，并用所有权排除规则阻止同一账户的买家流量消费其自己接入的卖家 Key。客户端角色判断仅用于体验，不得替代本功能。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 按角色使用允许的能力 (Priority: P1)

作为已登录用户，我希望账户只能访问与其角色匹配的能力，避免他人伪造身份操作我的资产或凭证。

**Independent Test**: 使用 `buyer`、`seller`、`both` 三类账户分别调用买家和卖家受保护能力，验证权限矩阵。

**Acceptance Scenarios**:

1. **Given** `buyer` 用户已认证，**When** 请求买家代理 Key 能力，**Then** 授权通过；请求卖家原始 Key 管理时返回 403。
2. **Given** `seller` 用户已认证，**When** 管理自己拥有的卖家 Key，**Then** 授权通过；请求买家代理 Key 能力时返回 403。
3. **Given** `both` 用户已认证，**When** 分别使用买家或卖家能力，**Then** 两类角色检查均可通过，但仍受资源所有权和自买自卖规则约束。
4. **Given** 客户端请求体携带另一个用户的 `user_id`，**When** 服务端授权，**Then** 始终采用认证会话身份并拒绝越权资源访问。

---

### User Story 2 - 阻止自买自卖路由 (Priority: P1)

作为平台，我希望双角色用户的代理请求永远不会选中该用户自己拥有的卖家 Key，从根源上避免自买自卖和统计污染。

**Independent Test**: 构造包含本人和其他卖家 Key 的候选池，验证本人 Key 始终被排除；只有本人 Key 时返回无可用资源。

**Acceptance Scenarios**:

1. **Given** 候选池包含当前买家本人和其他卖家的可用 Key，**When** 生成路由候选集，**Then** 本人拥有的全部 Key 被排除。
2. **Given** 候选池只包含当前买家本人的 Key，**When** 请求路由，**Then** 返回无可用 Key，不允许作为降级选择本人 Key。
3. **Given** 卖家 Key 所有权刚发生变更，**When** 新请求到达，**Then** 授权使用持久事实或已可靠失效的缓存，不沿用陈旧所有权。

---

### User Story 3 - 审计敏感授权结果 (Priority: P2)

作为安全维护者，我希望越权、伪造身份和自路由尝试可追踪，但审计内容不暴露凭证。

**Acceptance Scenarios**:

1. **Given** 请求因角色或所有权被拒绝，**When** 写入审计事件，**Then** 事件包含操作者、动作、资源脱敏标识、原因和请求标识。
2. **Given** 正常高频代理请求通过授权，**When** 记录遥测，**Then** 不生成包含原始 Key 或完整代理 Key 的审计内容。

### Edge Cases

- 用户会话中的角色快照与数据库当前角色不一致。
- 用户在请求执行期间被 suspended 或 deleted。
- 资源 ID 合法但属于另一卖家，或资源已软删除。
- 缓存不可用或所有权缓存过期。
- 批量操作中一部分资源属于当前用户、另一部分不属于。
- 请求未认证但同时携带伪造的角色和用户标识。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 服务端 MUST 定义并执行默认拒绝的角色权限矩阵；未显式允许的动作一律拒绝。
- **FR-002**: `buyer` MUST 只能创建、撤销和使用自己的代理 Key，不得接入或管理卖家原始 Key。
- **FR-003**: `seller` MUST 只能接入和管理自己拥有的卖家 Key，不得签发或使用买家代理 Key。
- **FR-004**: `both` MAY 使用买家和卖家能力，但 MUST 同时满足对应动作的资源所有权检查。
- **FR-005**: 授权身份 MUST 来自 SF04 验证的会话；客户端提供的 user_id、seller_id、buyer_id 或 role 不得覆盖认证上下文。
- **FR-006**: suspended、deleted 或会话已撤销的账户 MUST 被拒绝所有受保护动作。
- **FR-007**: 卖家资源的读写 MUST 校验资源所有者等于当前认证用户；不存在与不属于当前用户的资源对外返回应避免泄露可枚举差异。
- **FR-008**: 路由候选生成 MUST 排除 `seller_id == buyer_id` 的全部 Key，且不得在无其他候选时降级绕过。
- **FR-009**: 角色、账户状态和所有权变更 MUST 在新请求上立即或在明确小于 1 秒的失效窗口内生效。
- **FR-010**: 角色拒绝、所有权拒绝、自路由阻止和账户停用 MUST 形成脱敏审计事件。
- **FR-011**: 批量敏感操作 MUST 对每个资源独立授权；默认采用全有或全无，除非具体接口契约明确支持部分成功。

### Engineering Requirements *(mandatory)*

- **ER-001 — Contracts**: 未认证返回 401，已认证但角色/所有权不足返回 403；资源不可枚举场景可统一为 404，策略必须在契约中一致。
- **ER-002 — Security & Privacy**: RBAC 与所有权校验必须位于服务端、默认拒绝；敏感操作包含审计和重放防护，错误不得披露其他用户资料。
- **ER-003 — Data Integrity**: 用户角色、状态和资源所有权以 PostgreSQL 为事实源；缓存只做加速且必须有可靠失效机制。
- **ER-004 — Performance & Capacity**: 缓存命中时授权判断 P95 小于 10 毫秒，回源判断 P95 小于 50 毫秒。
- **ER-005 — Reliability**: 事实源不可达且无法确认权限时必须失败关闭；不得用“允许”作为缓存错误降级。
- **ER-006 — Observability**: 暴露按动作和拒绝原因聚合的授权计数，审计事件携带 correlation/request ID，禁止凭证和完整手机号。
- **ER-007 — Accessibility**: V0.1 无前端；错误码应稳定区分重新登录、角色不足和资源不可用，便于未来界面提供准确提示。

### Failure and Recovery Scenarios *(mandatory)*

1. **Given** 权限缓存不可用，**When** 敏感请求到达，**Then** 回源事实库；事实库也不可用时拒绝请求并记录故障。
2. **Given** 角色变更与请求并发，**When** 请求进入授权阶段，**Then** 按明确版本读取一致角色，不出现一半按旧角色、一半按新角色的写入。
3. **Given** 审计写入暂时失败，**When** 敏感状态变更准备提交，**Then** 该变更不得在无法满足强制审计的情况下静默成功；使用可恢复机制补写或整体回滚。

### Key Entities

- **Authorization Policy**: 角色、动作、资源类型和条件的默认拒绝规则；版本化并由领域所有者维护。
- **Resource Ownership**: 用户与卖家 Key、代理 Key 的所有权关系；以持久层为事实源。
- **Authorization Audit Event**: 操作者、动作、资源脱敏引用、决策、原因、策略版本、时间和请求标识；不可修改且有保留策略。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 权限矩阵中所有禁止组合的自动化测试拒绝率为 100%，允许组合成功率为 100%。
- **SC-002**: 包含本人 Key 的 1000 次路由候选生成中，本人 Key 被选择次数为 0。
- **SC-003**: 角色或账户状态变更后 1 秒内，100% 新请求采用新状态。
- **SC-004**: 缓存命中授权 P95 小于 10 毫秒，且缓存/数据库故障时不存在失败开放。
- **SC-005**: 100% 敏感拒绝和状态变更可按请求标识查询到脱敏审计事件。

## Scope

### In Scope

- 买家、卖家、双角色权限；账户状态；资源所有权；自路由排除；敏感授权审计。

### Out of Scope

- 管理员权限、角色升级/降级流程、实名认证、前端路由守卫和计费防套利。

## Test Requirements

- 权限矩阵表驱动单元测试覆盖全部角色/动作组合。
- 集成测试覆盖资源所有权、软删除、账户停用和审计事务。
- 负面测试覆盖身份字段伪造、IDOR、缓存故障、过期会话和批量混合所有权。
- 并发测试覆盖角色/所有权变更与请求竞争。
- 授权领域至少 80% 行覆盖，拒绝、自买自卖和失败关闭分支必须直接覆盖。

## Assumptions

- 依赖 SF03 的角色与状态、SF04 的认证上下文。
- SF13 消费本功能产生的“排除卖家 ID”约束；本功能不实现实际轮询算法。
- 当前采用 `both + 自路由排除`；若产品改为角色互斥，需先修订父索引和本 Spec。
