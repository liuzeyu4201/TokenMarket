# Feature Specification: SF02 本地依赖环境生命周期

**Feature ID**: `SF02`  
**Short Name**: `local-dev-environment`  
**Created**: 2026-07-13  
**Status**: Draft  
**Source**: 周度 Spec F01、架构规范、DevOps 规范

## 目标与价值

为 TokenMarket 开发者提供可重复、可诊断的本地依赖环境。开发者通过统一命令启动 PostgreSQL 15、Redis 7 和 Grafana，并能通过健康状态确认依赖可用；业务服务仍以本地进程运行以支持快速反馈。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一键启动本地依赖 (Priority: P1)

作为开发者，我希望一次启动所有 V0.1 必需中间件，并在 60 秒内知道它们是否真正可用。

**Independent Test**: 在无现存容器的开发机运行 `make dev`，验证三个依赖的健康状态、端口和网络访问。

**Acceptance Scenarios**:

1. **Given** 容器运行时可用且本地配置合法，**When** 执行 `make dev`，**Then** PostgreSQL 15、Redis 7 和 Grafana 在 60 秒内通过健康检查。
2. **Given** 依赖已经运行，**When** 再次执行 `make dev`，**Then** 不创建重复实例、不丢失数据库数据并返回成功。
3. **Given** 某端口被占用，**When** 执行启动，**Then** 命令明确指出冲突端口和服务，不把部分启动误报为成功。

---

### User Story 2 - 安全停止并重新启动环境 (Priority: P1)

作为开发者，我希望停止环境时释放运行资源，同时保留需要持久化的本地数据库数据。

**Independent Test**: 启动环境、写入测试数据、执行 `make dev-down`、重新启动并验证数据库数据仍在而 Redis 缓存可重建。

**Acceptance Scenarios**:

1. **Given** 本地依赖正在运行，**When** 执行 `make dev-down`，**Then** 所有相关容器停止且命令可重复执行。
2. **Given** PostgreSQL 中有本地测试数据，**When** 停止后重新启动，**Then** 数据仍存在，除非开发者显式执行带数据清理语义的独立操作。

---

### User Story 3 - 业务服务按名称连接依赖 (Priority: P2)

作为服务开发者，我希望容器内服务可通过稳定服务名访问依赖，本地进程可通过文档化地址访问同一依赖。

**Acceptance Scenarios**:

1. **Given** 本地依赖已就绪，**When** 运行网络连通性检查，**Then** 容器网络中的服务名和主机暴露端口均按约定可用。
2. **Given** 依赖尚未就绪，**When** 业务服务检查 readiness，**Then** 服务不接受依赖持久化的业务请求并报告可诊断原因。

### Edge Cases

- 容器运行时未启动、镜像缺失或磁盘空间不足。
- 上次异常退出留下 stopped 容器、孤立网络或健康状态过期。
- PostgreSQL 可建立 TCP 连接但尚不能执行查询。
- Redis 可连接但配置要求的认证不匹配。
- Grafana 进程运行但数据源未配置或不可查询。
- 本地配置文件缺失、变量类型错误或包含生产环境标记。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `make dev` MUST 启动 PostgreSQL 15、Redis 7 和 Grafana 的版本受约束实例。
- **FR-002**: 启动流程 MUST 使用真实健康探测判断可用性，不得只根据容器“running”状态报告成功。
- **FR-003**: 三个必需依赖 MUST 在命令开始后 60 秒内进入健康状态，否则启动整体失败并列出未就绪依赖。
- **FR-004**: `make dev-down` MUST 停止本项目的本地依赖且保持幂等，不得停止无关项目资源。
- **FR-005**: 默认停止 MUST 保留 PostgreSQL 持久卷；破坏性清理必须是独立、显式且有确认语义的操作。
- **FR-006**: Redis MUST 被视为可重建缓存，不得作为任何 V0.1 持久事实的唯一副本。
- **FR-007**: 容器内组件 MUST 通过约定服务名通信；本地主机访问地址和端口 MUST 记录在开发文档中。
- **FR-008**: 本地环境 MUST 从被忽略的开发配置读取真实值，并在启动前校验必需变量；`.env.example` 只提供安全占位。
- **FR-009**: V0.1 本地环境 MUST NOT 把 Kafka、前端或业务服务作为 `make dev` 成功的强制条件。
- **FR-010**: 每个依赖 MUST 暴露可被开发者和自动化检查读取的健康结果。

### Engineering Requirements *(mandatory)*

- **ER-001 — Contracts**: 服务名、端口、健康检查和数据持久化语义属于本地环境契约，变更时须同步所有消费者与文档。
- **ER-002 — Security & Privacy**: 默认凭证只能用于隔离的开发环境；生产配置不得被本地默认值覆盖，日志不得打印连接密码。
- **ER-003 — Data Integrity**: PostgreSQL 是本地持久事实源；停止/启动不得隐式重建 Schema 或清空卷。
- **ER-004 — Performance & Capacity**: 冷启动 60 秒内完成；健康环境再次执行启动应在 15 秒内确认就绪。
- **ER-005 — Reliability**: 健康检查应区分 liveness 与 readiness；停止流程须等待优雅终止并处理重复调用。
- **ER-006 — Observability**: 启动结果须逐项显示依赖状态、等待时间和安全的访问地址，不显示秘密值。
- **ER-007 — Accessibility**: 无图形业务界面；命令状态需同时使用文字和退出码表达，不只依赖颜色或图标。

### Failure and Recovery Scenarios *(mandatory)*

1. **Given** 一项依赖启动失败而其他依赖已启动，**When** 启动超时，**Then** 命令返回失败并保留可诊断日志；修复原因后可直接重试到一致状态。
2. **Given** 开发机异常关机，**When** 再次启动，**Then** 环境复用或修复已有容器与网络，不要求手工删除持久卷。
3. **Given** PostgreSQL 数据需要显式重置，**When** 开发者执行破坏性清理，**Then** 操作需明确提示数据影响并与普通 `dev-down` 分离。

### Key Entities

- **Local Dependency Instance**: 依赖名称、固定版本、健康状态、端口、服务名和持久化策略。
- **Local Environment Configuration**: 非提交的开发环境真实配置；由 `.env.example` 定义字段，不得包含生产数据。
- **Dependency Health Result**: liveness、readiness、检测时间、延迟和安全错误摘要。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 全新环境中 95% 的正常启动在 60 秒内完成并通过三项 readiness 检查。
- **SC-002**: 连续执行 10 次启动/停止循环，无重复容器、无孤立网络且数据库测试数据保持完整。
- **SC-003**: 100% 端口冲突、配置缺失和依赖未就绪场景返回非零状态并指出具体依赖。
- **SC-004**: 容器内服务名连通性测试和本地主机端口连通性测试全部通过。
- **SC-005**: 配置及启动日志扫描不出现密码、令牌或提供商 Key。

## Scope

### In Scope

- V0.1 本地 PostgreSQL、Redis、Grafana 的启动、停止、健康检查、网络和持久卷语义。

### Out of Scope

- 业务服务自动启动、Kafka、生产部署、数据种子、前端、云资源和破坏性环境清理自动化。

## Test Requirements

- 启停集成测试覆盖冷启动、重复启动、重复停止、端口冲突和异常重启。
- 数据持久化测试验证 PostgreSQL 保留、Redis 可清空重建。
- 网络测试验证服务名和主机地址。
- 配置负面测试验证缺失、非法类型和危险生产默认值。

## Assumptions

- 依赖 SF01 的根工作流和安全配置示例。
- 开发者已安装项目支持的容器运行时。
- Grafana 只要求基础可访问和数据源就绪；具体看板由 SF19 交付。
