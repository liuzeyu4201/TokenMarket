# V0.2 架构升级与容量目标

## 1. 目标

V0.2 将 V0.1 的单机可运行主链升级为可公开部署的交易沙盒。系统必须支持 500 名不同买家同时活跃，并允许代理入口、业务服务和后台任务独立扩缩容；任何单个应用实例退出都不得造成账务丢失或协议语义变化。

## 2. 目标架构

请求链路为：负载均衡器 → Go Proxy Gateway → 原生协议适配器 → 路由决策 → Provider Connection。身份、Project、权限、价格与账本由 API/Billing/Admin Service 管理；PostgreSQL 是业务事实源，Redis 只承载可重建的会话、限流、短期容量和协调状态；用量事件通过可持久化 Outbox/队列投递，禁止以进程内队列作为唯一副本。

所有服务必须满足：

- 代理节点无本地业务状态，可水平扩容；配置通过版本号原子切换。
- Web 会话、幂等键、限流桶与资源亲和可跨节点解析。
- 请求身份、路由决策、价格版本、用量和账务事件具有统一关联 ID。
- 关键状态变更采用数据库事务、唯一约束或 compare-and-set，不能依赖“先查后写”。
- 数据面与管理面隔离资源池；管理后台故障不得中断已授权代理请求。
- 专享 Project 严格绑定指定连接，故障时关闭失败，不回退共享池。

## 3. 容量模型

| 场景 | 验收负载 | 持续时间 | 核心门槛 |
|---|---:|---:|---|
| 同时活跃买家 | 500 个不同买家 | 30 分钟 | 无跨租户泄漏、无身份串用 |
| 非流式代理 | 500 RPS | 30 分钟 | 成功率 ≥ 99.9%，平台新增 p95 延迟 ≤ 100 ms |
| 突发代理 | 1000 RPS | 5 分钟 | 无崩溃、无账务丢失，恢复后无积压失控 |
| 流式连接 | 500 条 SSE/WebSocket | 2 小时 | 非正常断开率 ≤ 0.5%，内存无持续无界增长 |
| 控制面 | 100 RPS 混合读写 | 30 分钟 | p95 ≤ 500 ms，错误率 ≤ 0.5% |

容量验收使用可控 mock upstream；每种协议另做小规模真实厂商冒烟测试。厂商耗时从“平台新增延迟”中分离统计。

## 4. 可靠性与恢复目标

- 数据面月度可用性目标：99.9%。
- 管理 API 与 Web UI 月度可用性目标：99.5%。
- PostgreSQL 业务数据 RPO ≤ 5 分钟，服务 RTO ≤ 30 分钟。
- 发布采用滚动升级；兼容迁移先扩展后收缩，必须有经验证的回滚步骤。
- 单节点终止、Redis 重启、数据库短暂断连、队列延迟和 upstream 超时均须注入验证。
- 恢复后必须证明幂等：不重复扣费、不重复入账、不丢失最终可结算用量。

## 5. 架构验收证据

每项架构 SF 必须附：拓扑和故障域说明、契约变更、迁移与回滚记录、基准测试原始结果、指标截图或查询、故障注入记录。仅“接口返回成功”不能作为架构验收完成证据。
