# Feature Specification: SF17 代理请求用量记录

**Feature ID**: `SF17`  
**Short Name**: `proxy-usage-metering`  
**Created**: 2026-07-13  
**Status**: Draft  
**Source**: 周度 Spec F08、Go 计量规范、Python 数据/幂等规范

## 目标与价值

为每次非流式或流式代理调用创建一条可审计、可对账的用量记录，包含买家、实际卖家 Key、模型、Token、耗时、状态和结束原因。V0.1 只记录，不计算价格、不扣余额、不产生收益或账单，也不强制依赖 Kafka。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 记录成功请求的官方用量 (Priority: P1)

作为平台验证人员，我希望每次成功代理调用都准确记录官方返回的输入、输出和总 Token，以验证计量链路可行。

**Independent Test**: 发起带确定 usage 的非流式和流式请求，核对持久记录与官方响应、路由决策和 request_id。

**Acceptance Scenarios**:

1. **Given** 非流式成功响应包含 usage，**When** 请求完成，**Then** 5 秒内创建一条 source=official 的用量记录，Token 与响应一致。
2. **Given** 流式响应末块包含 usage，**When** `[DONE]` 到达，**Then** 汇总并创建一条 source=official 的记录。
3. **Given** 1000 个唯一成功请求，**When** 所有记录处理完成，**Then** 恰好存在 1000 条唯一 request_id 记录。

---

### User Story 2 - 处理缺失 usage 和失败请求 (Priority: P1)

作为维护者，我希望用量来源和完整性清楚，不能把估算值伪装成官方结果或完全丢失失败调用。

**Independent Test**: 覆盖无 usage、上游前置失败、流中断、客户端取消和估算失败。

**Acceptance Scenarios**:

1. **Given** 成功响应没有 usage，**When** 有经过验证的兼容估算规则，**Then** 保存 source=estimated 并标记估算规则版本。
2. **Given** 请求在收到任何模型输出前失败，**When** 完成观察到达，**Then** 记录状态、耗时和 end_reason，Token 为 0、source=not_available。
3. **Given** 流已交付部分内容后中断，**When** 能从已观察事件可靠估算，**Then** 记录 partial=true 和已观察 Token；不能可靠估算时标记 not_available，而不是伪造 0 为官方值。

---

### User Story 3 - 幂等持久化且不阻塞响应 (Priority: P1)

作为买家，我希望计量记录不会拖慢响应；作为平台，我希望异步失败可恢复且不重复记录。

**Acceptance Scenarios**:

1. **Given** 同一完成观察被重放，**When** 以 request_id 入库，**Then** 只保留一条主记录并返回幂等成功。
2. **Given** 持久化服务暂时不可用，**When** 客户端响应完成，**Then** 响应不被计量失败阻塞，观察已进入可检测、可重试的持久路径。
3. **Given** 恢复后重试积压观察，**When** 入库完成，**Then** 最终记录数与唯一请求数一致。

### Edge Cases

- 官方 total_tokens 与 prompt+completion 不一致。
- 相同 request_id 携带不同完成观察。
- 响应成功但模型字段缺失，或路由 Key 信息不可用。
- 流中断后只收到部分多字节文本。
- 数据库提交成功但确认响应丢失导致重试。
- 异步缓冲满、进程崩溃或优雅关闭。
- 用量记录与路由审计暂时无法关联。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: SF12/SF15 每个请求 MUST 产生且只产生一个完成观察；SF17 以 request_id 作为全局幂等键。
- **FR-002**: 用量记录 MUST 包含 usage_id、request_id、proxy_key_id、api_key_id、buyer_id、seller_id、platform、model、prompt_tokens、completion_tokens、total_tokens、usage_source、partial、latency_ms、status_code、end_reason 和 created_at。
- **FR-003**: Token 字段 MUST 为非负整数；官方 total 与分项不一致时不得静默修改，记录协议异常并采用明确校验策略。
- **FR-004**: 官方 usage 存在时 MUST 优先使用并标记 source=official。
- **FR-005**: 官方 usage 缺失时 MAY 使用经兼容测试验证、带版本的估算规则，并标记 source=estimated；无法估算标记 not_available。
- **FR-006**: 未产生输出的失败请求 MUST 记录 Token=0、source=not_available、实际状态和耗时。
- **FR-007**: 已产生部分流输出的失败请求 MUST 标记 partial；只在可证明的观察或估算基础上记录 Token。
- **FR-008**: 相同 request_id 和相同观察重放 MUST 幂等成功；相同 request_id 配不同关键字段 MUST 标记冲突并进入人工/告警核查。
- **FR-009**: 计量提交 MUST 不等待持久化完成后才交付客户端响应，但请求上下文销毁前观察必须进入可恢复的持久重试路径。
- **FR-010**: 正常情况下记录 MUST 在请求完成后 5 秒内可查询；积压和失败必须可观测并可重放。
- **FR-011**: 用量主记录 MUST 不可就地修改；修正使用关联原记录的补偿/更正记录并保留原因。
- **FR-012**: V0.1 原始用量记录默认保留 30 天；到期删除/匿名化策略必须保留验证所需聚合且不包含请求正文。
- **FR-013**: 记录 MUST NOT 包含消息内容、响应文本、完整代理 Key、原始 Key、手机号或认证头。
- **FR-014**: V0.1 MUST NOT 计算金额、扣减买家余额、增加卖家收益或发布计费事件。

### Engineering Requirements *(mandatory)*

- **ER-001 — Contracts**: 完成观察和用量记录 Schema 必须版本化；字段含事件/请求 ID、类型、版本、时间、生产者和 correlation ID。
- **ER-002 — Security & Privacy**: 仅保存最小元数据和脱敏 ID；请求/响应正文与凭证禁止进入记录、日志和重试载荷。
- **ER-003 — Data Integrity**: PostgreSQL 是用量事实源；request_id 唯一、Token 约束、不可变更正、幂等和日级记录数对账为强制要求。
- **ER-004 — Performance & Capacity**: 主请求提交观察 P95 小于 10 毫秒；正常记录 5 秒内可查；持续 >100 QPS 时不丢观察。
- **ER-005 — Reliability**: 可恢复队列、重试上限、积压背压、优雅关闭和进程崩溃恢复必须定义；不得依赖纯内存 fire-and-forget。
- **ER-006 — Observability**: 暴露观察产生/入库/重复/冲突/失败/积压/延迟/估算/缺失和日对账差异指标。
- **ER-007 — Accessibility**: V0.1 无用户界面；内部查询契约字段清晰并支持未来用量页面解释官方、估算和缺失。

### Failure and Recovery Scenarios *(mandatory)*

1. **Given** 数据库不可用，**When** 完成观察产生，**Then** 观察进入持久重试路径，客户端响应不被阻塞，恢复后幂等补写。
2. **Given** 入库成功但确认丢失，**When** 观察重试，**Then** 唯一约束返回原记录且不重复计数。
3. **Given** 同一 request_id 的载荷冲突，**When** 入库，**Then** 不覆盖原记录，保存冲突证据并触发高优先级完整性信号。

### Key Entities

- **Usage Completion Observation**: 网关产生的版本化完成事实，含关联 ID、路由、状态、耗时和 usage 完整性。
- **Usage Log**: PostgreSQL 中不可变的 V0.1 用量事实；无价值金额，不包含正文。
- **Usage Correction**: 对原 usage_id 的追加式修正、原因、操作者/来源和时间。
- **Usage Reconciliation Result**: 时间窗口内唯一请求数、观察数、记录数、重复和差异。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 1000 个唯一请求最终恰好产生 1000 条主用量记录，重复重放不增加数量。
- **SC-002**: 官方 usage 请求的 Token 字段与响应一致率 100%。
- **SC-003**: 95% 记录在请求完成后 5 秒内可查询，提交观察对主链路额外开销 P95 小于 10 毫秒。
- **SC-004**: 数据库 5 分钟故障恢复后积压观察全部补写，丢失数为 0、重复主记录为 0。
- **SC-005**: 失败、取消、超时、截断和 usage 缺失场景记录覆盖率 100%，来源和 partial 标记准确。
- **SC-006**: 用量表、重试载荷、日志和错误扫描不出现消息正文或任何完整凭证。

## Scope

### In Scope

- 非流式/流式完成观察、官方/估算/缺失 Token、失败结果、幂等持久化、恢复和对账。

### Out of Scope

- 价格、余额、计费、账单、收益、Kafka、长期财务流水和用户用量前端。

## Test Requirements

- Token 校验、估算版本、partial 和错误状态单元测试。
- 数据库集成测试覆盖唯一、不可变、迁移、回退与更正记录。
- 故障注入覆盖数据库中断、进程崩溃、积压、确认丢失和载荷冲突。
- 1000/高并发对账与性能测试验证数量、延迟和零丢失。
- 计量领域至少 80% 行覆盖，幂等、恢复和冲突分支直接覆盖。

## Assumptions

- 依赖 SF12、SF15 的唯一完成观察和 SF07 的 usage 解析。
- V0.1 不强制 Kafka；实施可选其他机制，但必须满足可恢复与不阻塞要求。
- 30 天保留用于技术验证，不构成后续财务记录保留政策。
