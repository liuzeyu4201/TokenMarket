## Clarifications

### Session 2026-07-15

- Q: SF02 完成时，业务服务的 dependency-aware readiness 应实现到什么范围？ → A: 仅 API Service 和 Billing Service 接入 PostgreSQL readiness；其他服务在真正引入依赖时再接入。
- Q: 缺失依赖镜像时，`make dev` 应如何处理，60 秒启动预算从哪里开始？ → A: 自动获取缺失的固定不可变镜像，获取阶段单独报告，60 秒 readiness 预算从镜像可用后开始。
- Q: 不同 clone/worktree 的本地资源应如何获得唯一且可重算的所有权标识？ → A: 使用固定仓库前缀加规范化工作区根路径的不可逆短哈希。
- Q: 本地连接地址和端口应以哪套配置作为事实源？ → A: 使用 `DATABASE_URL`、`REDIS_URL`、`GRAFANA_URL` 作为本地主机连接事实源，由生命周期严格校验并解析。
- Q: SF02 必须正式支持哪些本地主机平台？ → A: 支持 macOS arm64 与 Linux x86_64，行为契约一致且性能指标分别验证。

### Session 2026-07-16

- Q: Workflow event v2 应采用什么结构？ → A: 标准事件信封。
- Q: v2 公共生命周期应在什么时候正式激活？ → A: 双平台验收后激活。
- Q: 同一工作区已有生命周期操作持锁时，并发的第二个 `make dev` 应如何处理？ → A: 立即失败并重试。
- Q: FR-027 的“不得重写依赖锁”应限定在哪个阶段？ → A: 仅禁止运行时改锁。
- Q: ADR 002 应在什么时候标记为 `Accepted`？ → A: 实施前接受设计。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一次启动并确认依赖真正可用 (Priority: P1)

作为 TokenMarket 开发者，我希望通过仓库根目录的稳定入口一次启动 V0.1 必需的本地依赖，并在有限时间内获得逐项就绪结论，以便业务服务可以在本地进程中安全连接，而不必手工拼接多个生命周期命令。

**Why this priority**: 后续需要持久化、缓存或查看基础监控状态的开发活动都依赖可信的本地环境；仅看到进程存在而不能确认实际可用，会造成迁移、测试和故障定位结果不可靠。

**Independent Test**: 在受支持、无本项目运行实例的开发机上准备合法本地配置并执行 `make dev`；验证固定镜像全部可用并完成身份校验后才开始 60 秒 readiness 计时，三个必需依赖均在该预算内分别通过真实就绪检查，命令返回成功并显示安全的连接信息。

**Acceptance Scenarios**:

1. **Given** 受支持的容器运行时可用、声明的依赖镜像已可用且本地配置合法，**When** 开发者执行 `make dev`，**Then** PostgreSQL 15、Redis 7 和 Grafana 在固定镜像完成身份校验后的同一 60 秒 readiness 预算内分别通过就绪检查，且整体仅在三项全部就绪后返回成功。
2. **Given** 一个或多个声明镜像在本机缺失，**When** 开发者执行 `make dev`，**Then** 命令只获取契约声明的固定不可变镜像、单独报告获取结果，并在镜像全部可用后开始 60 秒 readiness 计时。
3. **Given** 三项依赖已经健康运行，**When** 开发者再次执行 `make dev`，**Then** 命令复用现有项目资源、不创建重复实例、不改变持久数据，并在 15 秒内确认成功。
4. **Given** 一个声明的主机端口被无关进程或其他项目占用，**When** 开发者执行 `make dev`，**Then** 命令在创建新的项目资源前失败，指出冲突端口与对应依赖，并且不把已有或部分状态误报为整体成功。
5. **Given** 一项依赖未在时限内就绪而其他依赖已经运行，**When** 启动等待结束，**Then** 命令返回失败、逐项显示最终状态和安全诊断，并保留可检查且可直接重试的项目状态。

### User Story 2 - 非破坏性停止并安全恢复 (Priority: P1)

作为 TokenMarket 开发者，我希望通过稳定入口停止本项目的本地依赖、释放运行资源并保留本地持久数据，以便稍后重新启动时能够继续开发，且不会影响其他项目或需要手工清理未知状态。

**Why this priority**: 停止操作与启动同样频繁；如果普通停止会删除数据、命中其他项目资源或无法从中断状态恢复，本地环境就不具备可重复使用的生命周期语义。

**Independent Test**: 启动环境，写入一条本地数据库标记数据，执行 `make dev-down` 两次，再执行 `make dev`；验证本项目运行资源已停止、第二次停止仍成功、重新启动后数据库标记仍存在，且缓存可以在无持久事实损失的情况下重建。

**Acceptance Scenarios**:

1. **Given** 本项目依赖正在运行，**When** 开发者执行 `make dev-down`，**Then** 命令只停止并移除本项目的运行实例和临时网络，等待受控终止，保留所有命名数据卷并返回逐项结果。
2. **Given** 本项目当前没有运行实例或上一次停止已经完成，**When** 开发者再次执行 `make dev-down`，**Then** 命令不把“已经停止”视为错误，不触及无关项目资源，并返回成功。
3. **Given** PostgreSQL 中存在本地测试数据，**When** 开发者停止后重新启动环境，**Then** 数据仍然存在，且启动过程不会隐式重建 Schema、执行迁移或写入种子数据。
4. **Given** 本地真实配置缺失或已损坏但项目资源仍在运行，**When** 开发者执行 `make dev-down`，**Then** 停止入口仍能根据已提交的项目身份安全定位本项目资源，不要求读取或回显秘密值。

### User Story 3 - 使用稳定地址连接并诊断不可用状态 (Priority: P2)

作为服务开发者，我希望容器内消费者通过稳定服务名访问依赖，本地主机进程通过文档化地址访问相同依赖，并能从就绪状态中区分“进程存活”与“可以处理请求”，以便快速定位配置、认证、网络和初始化问题。

**Why this priority**: 稳定连接契约和可诊断就绪状态减少每个服务自行猜测地址、端口和健康语义的风险，并防止依赖尚未可用时接受需要持久化的操作。

**Independent Test**: 环境就绪后，分别从项目容器网络和本地主机执行每项依赖的连接检查；随后使一项依赖进入“存活但未就绪”状态，验证消费者能够报告具体依赖原因，而不是把 TCP 可连接误判为可用。

**Acceptance Scenarios**:

1. **Given** 本地依赖全部就绪，**When** 从项目容器网络按契约服务名访问并从本地主机按输出地址访问，**Then** 三项连接路径均成功，且文档、配置定义和运行输出使用同一有效地址。
2. **Given** PostgreSQL 可以建立网络连接但不能完成认证或执行最小查询，**When** 运行就绪检查，**Then** PostgreSQL 被报告为未就绪并返回不含凭证的原因。
3. **Given** Redis 进程存活但认证配置不匹配，**When** 运行就绪检查，**Then** Redis 被报告为未就绪，不把简单端口连通视为成功。
4. **Given** Grafana 进程存活但其健康接口或本地管理员认证不可用，**When** 运行就绪检查，**Then** Grafana 被报告为未就绪；实时指标数据源和业务看板不作为 SF02 的成功条件。
5. **Given** API Service 或 Billing Service 的本地 PostgreSQL 尚未就绪，**When** 服务计算 readiness，**Then** liveness 保持独立，readiness 报告 PostgreSQL 不可用，且需要持久化的操作不会被误报为可处理；其他服务不在 SF02 中提前接入未声明依赖。

### Edge Cases

- 容器运行时未安装、未启动、版本不受支持或当前用户无访问权限。
- 固定身份的依赖镜像不存在、无法获取、校验不匹配或磁盘空间不足。
- 一个或多个主机端口被占用，或端口在预检后、实际绑定前被并发抢占。
- 上次异常退出留下 stopped 容器、孤立网络、已存在的数据卷或过期健康状态。
- 两个终端并发执行 `make dev`，或 `make dev` 与 `make dev-down` 同时执行。
- 开发者在启动或停止过程中发送中断信号，或容器运行时在生命周期中途退出。
- PostgreSQL 可建立 TCP 连接但认证失败、目标数据库不存在或无法执行最小查询。
- Redis 可连接但认证不匹配，或响应来自占用该端口的非项目实例。
- Grafana 进程运行但健康接口、管理员认证或基础配置不可用。
- 本地配置文件缺失、必需值为空、格式错误、仍使用不可用占位符、引用生产地址或声明非本地模式。
- 工作区路径包含空格或非 ASCII 字符，终端不支持颜色、图标或交互输入。
- 工作区被移动或重命名后计算出新的资源标识，而旧路径标识下仍有停止的容器、网络或数据卷。
- 在 macOS arm64 与 Linux x86_64 上出现不同的路径解析、回环绑定、容器网络或停止信号行为。
- 已停止环境中的缓存或可视化本地状态丢失，但任何持久业务事实不得因此丢失。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 仓库 MUST 保留 `make dev` 与 `make dev-down` 作为本地依赖生命周期的唯一公开入口，且不得改变目标名称、整体退出语义或根 Makefile 的公开入口地位。SF02 的实现候选 MAY 在功能分支中接受测试，但只有全部仓库事件消费者完成 v2 迁移，且 Linux x86_64 与 macOS arm64 的生命周期、隔离、持久化、脱敏、恢复和性能验收全部通过后，才 MUST 以同一受评审变更激活真实 `dev`/`dev-down`、event v2 和帮助/恢复文档并替换 SF01 的 `SF02_NOT_READY` 过渡失败。
- **FR-002**: `make dev` 的 V0.1 必需依赖集合 MUST 严格限定为 PostgreSQL 15、Redis 7 和 Grafana；Kafka/Redpanda、Prometheus、Loki、MinIO、前端及任何业务服务均不得成为本功能启动成功的条件。
- **FR-003**: 每项必需依赖 MUST 使用受版本约束且身份可验证的不可变发布物；浮动 `latest` 标识不得作为可复现启动依据。声明镜像缺失时，`make dev` MUST 只自动获取契约中固定的镜像身份、验证获取结果并单独报告该阶段；获取失败或身份不匹配 MUST 在创建依赖实例前返回失败。依赖版本或身份变更 MUST 作为受评审的契约变更处理。
- **FR-004**: `make dev` MUST 在创建或修改项目资源前验证本地模式、必需配置、受支持容器运行时和已声明主机端口；失败 MUST 返回非零状态，只指出不安全或无效字段的名称及修复方向，不得输出字段值。
- **FR-005**: 本地环境 MUST 只接受明确的本地模式和被版本控制忽略的本地真实配置；`DATABASE_URL`、`REDIS_URL` 和 `GRAFANA_URL` MUST 是本地主机连接地址与端口的唯一事实源，其中数据库与缓存 URL 必须携带所需合成认证信息，Grafana 管理密码必须由独立秘密字段提供。测试或生产模式、非回环主机、生产地址、不可用示例占位符及缺失的必需认证值 MUST 在资源访问前被拒绝。
- **FR-006**: 被提交的 `.env.example` 或等价配置定义 MUST 声明 `DATABASE_URL`、`REDIS_URL`、`GRAFANA_URL`、Grafana 管理密码及其他必需字段的名称、用途、类型、环境范围、敏感级别和不可用安全占位符；本功能不得提交、生成或回显真实密码、令牌、提供商 Key 或生产数据。
- **FR-007**: 容器网络中的规范服务名 MUST 为 `postgres`、`redis` 和 `grafana`；本地主机 URL 的默认端口 MUST 分别为 5432、6379 和 3000。主机地址或端口覆盖 MUST 仅通过修改对应 URL 表达，并同步到文档、运行输出和本地消费者；不得再引入一套独立端口字段作为竞争事实源。
- **FR-008**: 生命周期 MUST 严格解析并校验三个本地主机 URL，再以其中的认证、数据库和端口信息配置依赖；容器内地址 MUST 仅将主机部分替换为规范服务名后派生，不得要求开发者维护第二套容器 URL。
- **FR-009**: 主机暴露端口 MUST 默认仅绑定回环接口；容器内消费者 MUST 通过项目隔离网络和规范服务名通信，不得要求开发者把本地依赖暴露到局域网或公网。
- **FR-010**: 启动前端口检查 MUST 区分本项目已运行实例与无关占用者；无关端口冲突 MUST 在创建新资源前失败，列出冲突端口和依赖，但不得停止或重配置占用者。
- **FR-011**: 每项依赖 MUST 同时具有可观察的 liveness 与 readiness 结论；readiness 不得仅依据容器或进程处于 running 状态。
- **FR-012**: PostgreSQL readiness MUST 使用本地合成凭证连接目标数据库并成功执行无副作用最小查询；Redis readiness MUST 使用约定认证完成命令往返；Grafana readiness MUST 验证健康接口和本地管理员认证。SF02 不要求可查询的实时指标数据源或业务看板。
- **FR-013**: `make dev` MUST 在声明镜像全部可用后开始独立的 60 秒 readiness 预算，并在该预算内等待三项必需依赖全部就绪；镜像获取耗时不得计入 readiness 预算。任何一项超时或失败时整体 MUST 失败，逐项报告状态、等待时间和已脱敏原因，且不得把部分成功表示为整体成功。
- **FR-014**: 对已经健康的环境重复执行 `make dev` MUST 在 15 秒内完成确认，不创建重复容器、网络或数据卷，不改变已有持久数据，并安全复用当前资源。
- **FR-015**: 启动失败后，工作流 MUST 保留本项目资源的可检查状态与诊断获取方式，不得自动删除或重建数据卷；开发者修复原因后 MUST 能直接重试并收敛到与干净启动相同的健康状态。
- **FR-016**: 本地资源所有权标识 MUST 由固定仓库前缀和规范化工作区根路径的不可逆短哈希组成；同一路径跨分支切换和重启 MUST 得到相同标识，不同 clone/worktree MUST 得到不同标识。原始路径不得进入资源名称、标签、日志或事件。
- **FR-017**: `make dev-down` MUST 只停止并移除当前工作区标识拥有的运行实例和临时网络，等待受控终止，保留全部命名数据卷；重复停止或资源已不存在时 MUST 保持幂等成功。
- **FR-018**: `make dev-down` MUST 能在本地秘密配置缺失或非法时重新计算工作区标识并执行安全停止；用于识别项目资源的前缀、哈希规则、名称与所有权标签 MUST 来自已提交且不敏感的契约，不得依赖连接密码。
- **FR-019**: 工作区移动或重命名后 MUST 生成新标识；生命周期命令 MUST NOT 自动接管或停止旧标识资源，但 MUST 能发现同一仓库前缀下的旧资源并提供不含原始路径的显式恢复指引。
- **FR-020**: PostgreSQL 持久卷 MUST 跨普通停止、重新启动、失败重试和开发机异常重启保留；启动或停止 MUST NOT 隐式创建业务 Schema、运行迁移、写入种子数据或清空卷。
- **FR-021**: Redis MUST 被视为可重建状态，不能成为 V0.1 持久事实的唯一副本；普通停止仍不得删除其命名卷，但任何验收和恢复流程 MUST 能在 Redis 内容为空时恢复正确行为。
- **FR-022**: 破坏性数据清理自动化 MUST NOT 由本功能交付，也不得隐藏在 `make dev-down`、启动失败恢复或任何普通重试中；未来如新增清理动作，必须使用独立公开语义、明确数据影响和强确认。
- **FR-023**: 同一工作区标识的全部生命周期改变操作 MUST 使用同一个非阻塞排他锁串行化；无论第二个命令是重复启动还是启动/停止冲突，未获得锁的命令 MUST 立即返回非零状态与 `OPERATION_IN_PROGRESS`，不得等待、复用活动命令结果或产生 Docker、探测、网络、容器、卷及其他破坏性副作用。调用者 MAY 在活动操作结束后显式重试。
- **FR-024**: 本地开发文档 MUST 记录必需前置条件、配置准备、资源标识与工作区移动语义、规范服务名、默认及有效主机地址、健康语义、启动/停止副作用、常见失败诊断和非破坏性恢复步骤。
- **FR-025**: SF02 MUST 仅为 API Service 和 Billing Service 接入 PostgreSQL dependency-aware readiness；PostgreSQL 未就绪时，两者必须保持 liveness 独立、在 readiness 中报告具体依赖并拒绝把需要持久化的操作表示为可处理。网关、Admin Service 及其他依赖的 readiness 接入 MUST 延后到相应功能明确引入依赖时，且任何业务服务均不得成为 `make dev` 的启动对象或成功条件。
- **FR-026**: 生命周期结果 MUST 使用 Root Make Workflow event v2 标准事件信封：顶层必须包含唯一 `event_id`、稳定 `event_type`、`schema_version`、UTC `timestamp`、`producer`、`correlation_id` 和 `payload`；`correlation_id` 是一次生命周期运行的关联标识，`payload` 至少包含动作、组件、阶段、状态、稳定诊断类别、耗时和安全消息，逐依赖阶段及依赖专属失败还 MUST 包含 `dependency`，聚合身份或最终结果 MAY 省略该字段。纯文本输出 MUST 表达同等安全语义；新增诊断类别或字段时 MUST 先更新版本化契约及其消费者测试。
- **FR-027**: `make dev`、`make dev-down`、bootstrap 及本功能交付的其他运行时路径 MUST NOT 安装或升级系统工具、生成或改写依赖锁、执行应用构建、运行数据库迁移、启动业务服务或访问任何共享测试/生产资源。实现阶段 MAY 通过独立受评审变更更新工作流工具自己拥有的依赖声明与锁文件，但 MUST 使用锁定命令、不得改变服务锁，并须通过锁漂移、依赖、安全与许可证门禁。
- **FR-028**: 生命周期与文档 MUST 正确处理包含空格或非 ASCII 字符的仓库路径，并保留所有用户未提交源码和未跟踪文件；除声明的本地运行资源外不得修改工作区状态。
- **FR-029**: SF02 MUST 正式支持 macOS arm64 与 Linux x86_64；两类平台 MUST 使用相同公开目标、配置字段、资源所有权、服务名、健康标准、持久化语义、输出和退出行为。平台适配不得形成第二套公开工作流，Windows、其他架构和不使用受支持容器运行时的原生依赖不属于本功能兼容承诺。

### Engineering Requirements *(mandatory)*

- **ER-001 — Contracts**: `make dev`/`make dev-down` 的名称、模式限制、依赖集合、规范服务名、主机端口、健康标准、资源所有权、数据卷语义、输出事件和退出行为属于版本化开发者契约；任何不兼容变更必须同步消费者、自动化测试、文档和迁移说明。
- **ER-002 — Security & Privacy**: 本地认证值必须为合成且只存在于被忽略配置或批准的本地秘密来源中；主机端口默认只绑定回环接口，非本地模式与生产地址失败关闭，命令、事件、健康错误、容器定义和测试夹具均不得暴露真实秘密。
- **ER-003 — Data Integrity**: PostgreSQL 是本地持久事实源，普通生命周期操作不得删除或隐式改写其数据和 Schema；Redis 只保存可重建状态。资源所有权必须阻止停止其他项目，失败、重试、并发和异常重启均不得产生重复持久卷或隐式数据重置。
- **ER-004 — Performance & Capacity**: 在 macOS arm64 与 Linux x86_64 的代表性开发机上，镜像获取作为单独阶段计时和报告；两类平台分别计算时，镜像可用后至少 95% 正常冷启动的 readiness 阶段必须在 60 秒内完成，健康环境的重复启动确认必须在 15 秒内完成。容量范围为每个工作区各一项必需依赖实例，不承诺本功能提供集群或高可用拓扑。
- **ER-005 — Reliability**: 生命周期操作必须幂等且同工作区串行化；启动采用总计不超过 60 秒的有界等待，停止等待受控终止并在失败时保留可重试状态。只有已证明安全的探测可自动重试，重试不得掩盖最终失败。
- **ER-006 — Observability**: 每次生命周期执行必须产生逐依赖、逐阶段的开始、等待、成功、失败或跳过状态及耗时，并提供安全日志查看或恢复指引；不得记录连接 URL 中的凭证、认证值、令牌或生产数据。API Service 与 Billing Service 的 PostgreSQL readiness MUST 分别暴露无秘密标签的 Prometheus 探测总数、失败总数和耗时直方图，并由自动化测试验证成功、失败和恢复路径会更新指标。仓库维护者是本地生命周期失败契约与运行手册的责任方，API/Billing 服务维护者分别拥有其 readiness 指标与诊断。
- **ER-007 — Accessibility**: 本功能无图形业务界面；帮助、进度、最终状态、警告和错误必须可由纯文本终端及屏幕阅读器理解，成功和失败同时通过文字与退出状态表达，不得只依赖颜色、Unicode 图标、动画或交互提示。

### Failure and Recovery Scenarios *(mandatory)*

1. **Given** 一项依赖启动失败而其他依赖已经运行，**When** 60 秒启动等待结束，**Then** 整体返回失败并保留项目资源、逐项状态和安全诊断；开发者修复原因后直接重试即可收敛，不删除或重建持久卷。
2. **Given** 两个生命周期命令重复或冲突执行，**When** 第二个命令未获得同一工作区的非阻塞排他锁，**Then** 工作流立即以 `OPERATION_IN_PROGRESS` 和非零状态拒绝该命令，不等待或复用活动命令结果，不创建重复资源、不删除数据，也不把跳过步骤报告为通过；活动操作结束后调用者可以显式重试。
3. **Given** 开发机、容器运行时或生命周期命令异常中断，**When** 开发者重新执行启动或停止，**Then** 工作流识别并协调已有容器、网络和数据卷，忽略过期健康状态，并在不要求手工删除持久卷的情况下恢复一致状态。
4. **Given** 运行时不受支持、配置非法、模式非本地或端口被无关进程占用，**When** 开发者执行启动，**Then** 命令在修改项目资源前失败，只显示安全的具体原因；修复后可直接重试。
5. **Given** 本地配置缺失但项目资源仍需停止，**When** 开发者执行 `make dev-down`，**Then** 工作流依据非敏感项目所有权完成或安全重试停止，不因缺少数据库或管理员密码而要求破坏性人工清理。

### Key Entities *(include if feature involves data)*

- **Local Dependency Definition**: 一项必需本地依赖的版本化契约，包含规范名称、发布物身份、服务名、默认主机端口、健康标准、持久化分类和所有者。仓库内受评审定义是事实源，不含秘密，随版本控制保留；变更必须同步消费者和兼容说明。
- **Local Environment Configuration**: 开发者工作区持有的本地模式配置，以 `DATABASE_URL`、`REDIS_URL` 和 `GRAFANA_URL` 作为本地主机连接与端口事实源，并以独立秘密字段保存 Grafana 管理密码。字段定义由仓库所有，真实值由开发者所有并保持未跟踪；内容按秘密处理，可由开发者随时轮换或删除，不进入遥测、测试夹具或版本控制。容器地址从这些 URL 和固定服务名派生，不形成第二套配置事实源。
- **Project Resource Set**: 一个工作区拥有的容器、隔离网络、命名数据卷和生命周期锁集合，以固定仓库前缀加规范化工作区根路径不可逆短哈希形成的标识与其他工作区区分。生命周期入口是其状态改变的唯一公开所有者；普通停止移除运行实例和临时网络，但保留命名数据卷。工作区移动产生新标识，旧标识资源只能被发现和显式恢复，不会被自动接管。
- **Dependency Health Result**: 单项依赖在一次检查中的 liveness、readiness、检测时间、耗时、状态和脱敏错误摘要。它是短期运行证据，不是持久事实源；过期结果不得在进程或环境重启后继续作为当前就绪结论。
- **Local Persistent Data**: PostgreSQL 命名卷中的合成本地开发数据。开发者是数据所有者，PostgreSQL 是本地事实源；普通生命周期操作必须保留它，删除不属于本功能，且其中不得包含复制自生产环境的未匿名化数据。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在声明前置条件满足的 macOS arm64 与 Linux x86_64 代表性开发机上分别统计时，至少 95% 的正常冷启动从固定镜像全部可用到三项必需依赖全部就绪不超过 60 秒；镜像缺失场景均单独记录获取耗时和结果。
- **SC-002**: 对健康环境连续执行 10 次重复启动确认，100% 在 15 秒内结束，且运行实例、隔离网络和命名数据卷数量不增加。
- **SC-003**: 连续执行 10 个完整启动/停止/重新启动循环后，不存在重复运行实例或孤立临时网络，指定持久测试记录 100% 保持完整，可重建状态为空时仍不造成持久事实损失。
- **SC-004**: 对运行时不可用、镜像不可用、端口冲突、配置缺失、占位符未替换、非本地模式、认证不匹配和依赖超时的预置场景，100% 返回失败并准确指出受影响依赖或配置名称，不出现部分成功误报。
- **SC-005**: 项目网络服务名与本地主机有效地址的全部连通性检查均通过，文档、配置定义和命令输出中的地址匹配率达到 100%。
- **SC-006**: 普通停止、重复停止、失败重试和异常重启验证中，指定持久测试记录保留率达到 100%，且无一次操作停止或删除无关项目资源。
- **SC-007**: 对本地配置、纯文本输出、结构化事件、健康错误和可诊断日志进行扫描，密码、令牌、提供商 Key、生产地址及未匿名化生产数据泄露数为 0。
- **SC-008**: 至少 90% 的代表性新项目开发者能够只依靠根帮助和本地环境文档，在 10 分钟内完成配置准备、启动、确认三项状态并找到一个注入故障的恢复指引。
- **SC-009**: 100 次并发重复或冲突生命周期测试中，不产生重复资源、数据卷删除或无关资源变更；失去执行权的命令均给出明确且可重试的结果。

## Assumptions

- 目标用户是 TokenMarket 开发者和持续集成维护者，不是买家、卖家、管理员或生产运维操作员。
- SF01 已交付根 Makefile、锁定工具链检查、安全配置定义、纯文本与结构化事件输出契约；SF02 只替换 `dev`/`dev-down` 的 `SF02_NOT_READY` 过渡适配，不建立第二套公开工作流。
- 开发者已安装 SF01 声明的受支持容器运行时；本功能负责检测与提示，不负责安装、升级或授权系统工具。
- “正常冷启动”指本工作区没有运行中的项目实例且配置合法；`make dev` 会在 readiness 计时前自动获取并验证缺失的固定不可变镜像。镜像获取失败或耗时单独报告，不得被计入或误报为依赖健康失败。
- `DATABASE_URL`、`REDIS_URL` 和 `GRAFANA_URL` 的默认主机端口为 5432、6379 和 3000，且主机只允许回环地址；确需覆盖时直接修改对应 URL，不改变容器网络中的规范服务名。
- 工作区资源标识不依赖 Git 分支或秘密配置；工作区根路径移动或重命名被视为创建新的本地资源命名空间。
- macOS arm64 与 Linux x86_64 是 SF02 的完整支持矩阵；两类平台均已安装 SF01 声明的受支持容器运行时与 Compose 能力，其他主机平台不作为验收阻塞项。
- 普通停止保留全部命名数据卷；Redis 内容和 Grafana 本地状态可重建或丢弃，但任何持久业务事实只能以 PostgreSQL 为本地事实源。
- Grafana 在 SF02 中只需健康接口和本地认证可用；Prometheus 数据源、实时查询、告警和业务看板由 SF19 或后续监控功能交付，不扩大 `make dev` 的依赖集合。
- 本地环境只使用合成数据和合成凭证；生产数据不得直接复制到该环境，除非已不可逆匿名化并获得明确批准。

## Scope

### In Scope

- PostgreSQL 15、Redis 7 和 Grafana 的本地启动、真实健康检查、非破坏性停止、重复执行、异常恢复和并发保护。
- 项目隔离网络、规范服务名、回环主机端口、命名数据卷及其所有权和持久化语义。
- `make dev` 与 `make dev-down` 从 SF01 过渡失败到真实生命周期的契约兼容迁移。
- 本地配置校验、秘密防护、逐项状态输出、稳定诊断类别和开发者恢复文档。
- API Service 与 Billing Service 的 PostgreSQL liveness/readiness 区分及本地连接契约验证，但不启动业务服务；其他服务的依赖接入不属于 SF02。
- macOS arm64 与 Linux x86_64 的一致生命周期行为及独立性能验收。

### Out of Scope

- Kafka、Redpanda、Prometheus、Loki、MinIO、对象存储或其他可选基础设施的本地生命周期。
- 前端、代理网关或任何 Python 业务服务的自动启动、热重载和进程管理。
- 业务 Schema 创建、数据库迁移、数据种子、生产数据复制和破坏性数据清理自动化。
- 实时指标数据源、Grafana 业务看板、告警规则和外部通知；这些由 SF19 或后续监控功能负责。
- 测试环境或生产环境部署、云资源、Kubernetes、高可用集群和系统工具安装。
- Windows、macOS x86_64、Linux 非 x86_64、其他主机平台及不使用受支持容器运行时的原生依赖生命周期。
- 用户、角色、提供商凭证、代理、路由、计量、计费、管理或其他 TokenMarket 业务行为。

## Verification Requirements

- 生命周期契约测试覆盖公开目标、模式限制、退出语义、SF01 过渡替换、输出事件和秘密脱敏。
- 启停集成测试使用真实且版本兼容的依赖，覆盖冷启动、健康重复启动、重复停止、部分失败、超时、中断、异常重启和 10 轮数据保留循环。
- 负面测试覆盖运行时缺失或不受支持、固定镜像自动获取失败或身份不匹配、配置缺失或危险、端口冲突、认证不匹配、过期健康状态和无关资源隔离，并验证镜像获取耗时不计入 readiness 预算。
- 并发与隔离测试覆盖不同 clone/worktree 的标识唯一性、同一路径标识稳定性、重复启动、启动与停止冲突及锁持有者异常退出，证明无重复资源、无数据卷删除且可安全重试；路径移动场景验证旧资源只被报告而不被自动接管。
- 平台矩阵验收在 macOS arm64 与 Linux x86_64 上分别覆盖路径规范化、回环绑定、网络、健康、停止信号、数据保留以及 60 秒冷启动和 15 秒重复启动指标，并验证两类平台的公开输出契约一致。
- 配置与连通性测试验证三个 URL 的 scheme、回环主机、默认及覆盖端口、认证字段和派生容器地址，证明不存在竞争端口字段或第二套容器 URL；随后分别验证 PostgreSQL 查询、Redis 认证命令往返和 Grafana 健康/认证语义，API Service 与 Billing Service 的 readiness 测试直接覆盖 PostgreSQL 不可用分支。
- 安全测试扫描配置、输出、结构化事件、容器定义、日志和测试夹具，验证回环绑定、生产模式失败关闭及零秘密泄露。
- 文档验收由代表性新开发者仅按根帮助和本地环境指南完成首次启动、状态判断、停止和故障恢复。
