# Feature Specification: SF18 结构化日志与全链路请求关联

**Feature ID**: `SF18`  
**Short Name**: `structured-request-logging`  
**Created**: 2026-07-13  
**Status**: Draft  
**Source**: 周度 Spec F10、架构请求标识规范、Python/DevOps 日志规范

## 目标与价值

为所有 V0.1 服务、代理请求和后台检查提供统一 JSON 结构化日志与全链路请求/关联标识，使维护者可以还原一次请求的认证、路由、上游、计量和响应过程，同时保证凭证、个人数据和模型正文不会进入日志。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 用单一标识排查代理请求 (Priority: P1)

作为开发和运维人员，我希望输入 request_id 后可以找到网关各阶段及相关用量记录的日志，快速确定失败位置。

**Independent Test**: 执行一次成功和一次失败代理请求，按 request_id 查询并验证事件顺序和必需字段。

**Acceptance Scenarios**:

1. **Given** 客户端提供合法 X-Request-ID，**When** 请求贯穿系统，**Then** 各阶段日志和响应使用同一 request_id。
2. **Given** 客户端未提供或提供非法/冲突标识，**When** 请求开始，**Then** 网关生成唯一标识并透传所有下游。
3. **Given** 请求成功或失败，**When** 按 request_id 查询，**Then** 能看到开始、认证结果、路由结果、上游结果、完成/计量结果和总耗时，且顺序可解释。

---

### User Story 2 - 获取一致的机器可读日志 (Priority: P1)

作为维护者，我希望 Go、Python 和后台任务使用统一字段，使日志可以被同一采集与查询规则处理。

**Independent Test**: 采集各组件代表性日志，验证每行是单个合法 JSON 对象且满足 Schema。

**Acceptance Scenarios**:

1. **Given** 任一服务记录事件，**When** 输出日志，**Then** 每行 JSON 至少含 timestamp、level、service、version、environment、operation、correlation/request ID 和 outcome。
2. **Given** 事件包含 HTTP 或平台调用，**When** 完成，**Then** 可安全附加 method、path template、status_code、latency_ms、platform 和脱敏资源 ID。

---

### User Story 3 - 防止日志泄露敏感信息 (Priority: P1)

作为用户和 Key 所有者，我希望任何正常、错误或 panic 路径都不会把凭证或模型内容写入日志。

**Acceptance Scenarios**:

1. **Given** 请求含手机号、验证码、访问令牌、代理 Key、卖家 Key 和聊天内容，**When** 正常及错误日志输出，**Then** 完整敏感值均不存在。
2. **Given** 上游错误正文或 panic 包含 Authorization 信息，**When** 记录诊断，**Then** 在序列化前被统一过滤或替换。

### Edge Cases

- 客户端提供超长、包含控制字符或与现有请求冲突的 X-Request-ID。
- 日志字段本身包含换行、不可编码值或循环对象。
- panic 堆栈、第三方库错误或 HTTP dump 携带凭证。
- 日志采集后端不可用或 stdout 写入变慢。
- request_id 在异步任务、goroutine 或重试中丢失。
- 高频逐事件日志导致流式请求性能下降或磁盘爆满。
- 用户 IP、User-Agent 等潜在个人数据被无边界记录。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 每个外部请求 MUST 具有唯一 request_id；后台任务和异步观察 MUST 具有 correlation_id，并在源请求存在时关联其 request_id。
- **FR-002**: 合法客户端 X-Request-ID MAY 被采用；系统 MUST 校验长度、字符集和冲突，非法值替换为服务端生成值。
- **FR-003**: 所有服务日志 MUST 每行输出一个合法 JSON 对象，禁止多行普通文本作为常规日志格式。
- **FR-004**: 基础字段 MUST 包含 RFC3339 timestamp、level、service、version、environment、operation/event、request_id/correlation_id、outcome 和安全消息。
- **FR-005**: HTTP 完成事件 SHOULD 包含 method、path template、status_code 和 latency_ms；代理事件 SHOULD 包含 platform、model 和脱敏 key_id，但不得包含 URL 查询秘密。
- **FR-006**: 密码、验证码、访问/刷新令牌、Authorization、Cookie、代理 Key、原始 Key、加密材料、完整手机号、聊天消息和响应内容 MUST 在序列化前删除或脱敏。
- **FR-007**: 默认 MUST NOT 记录请求/响应正文或完整 Header；确需诊断的字段须使用允许列表且经过数据分类评审。
- **FR-008**: 日志级别 MUST 具有统一含义；可预期客户端 4xx 不得一律记为 ERROR，系统完整性/上游持续失败须按严重度记录。
- **FR-009**: panic/recovery、后台任务错误、超时、取消和重试耗尽 MUST 保留安全错误类别与堆栈摘要，但先经过敏感过滤。
- **FR-010**: 异步和 goroutine 执行 MUST 显式携带关联上下文，不能创建无法关联的关键业务日志。
- **FR-011**: 流式代理 MUST 记录开始和最终汇总事件，不为每个内容 chunk 记录正文或高基数日志。
- **FR-012**: 日志后端不可用 MUST NOT 阻塞代理主链路；服务至少保留受控 stdout/stderr 降级并暴露丢弃/背压计数。
- **FR-013**: V0.1 详细运行日志默认保留 30 天，到期按数据分类删除；安全审计事件遵循各领域更长的独立保留要求。

### Engineering Requirements *(mandatory)*

- **ER-001 — Contracts**: 共享日志 Schema、字段类型、级别、request_id 传递头和脱敏规则须版本化，Go/Python 消费相同定义。
- **ER-002 — Security & Privacy**: 序列化前脱敏、默认正文禁记、日志访问最小权限、测试扫描和第三方错误过滤为强制要求。
- **ER-003 — Data Integrity**: request_id 在一次请求内不可变化；时间统一使用 UTC/RFC3339，日志仅为诊断记录，不替代业务事实源。
- **ER-004 — Performance & Capacity**: 结构化日志对非流式代理额外开销 P95 小于 5 毫秒；高流量场景受采样/汇总和背压策略保护。
- **ER-005 — Reliability**: 日志写入失败不得使业务 panic；缓冲有界、优雅关闭尽力 flush，丢弃必须计量而非静默。
- **ER-006 — Observability**: 日志系统自身暴露写入失败、丢弃、队列深度、采集延迟和解析失败，并有明确运维所有者。
- **ER-007 — Accessibility**: 日志为机器/运维接口；字段名、级别和消息必须可读，不只通过颜色或表情表达严重度。

### Failure and Recovery Scenarios *(mandatory)*

1. **Given** 日志聚合后端不可用，**When** 服务继续处理请求，**Then** 主链路不阻塞，受控本地输出继续，丢弃/积压可观测。
2. **Given** 第三方错误包含完整凭证，**When** recovery 记录异常，**Then** 敏感过滤在 JSON 序列化前移除值，安全扫描通过。
3. **Given** 进程优雅关闭，**When** 日志缓冲仍有事件，**Then** 在有界时间内 flush；未完成数量被计量并记录恢复说明。

### Key Entities

- **Log Event**: 版本化 JSON 诊断事件，包含安全上下文和关联标识，不是业务事实源。
- **Correlation Context**: request_id、correlation_id、服务与操作边界的传播信息。
- **Redaction Policy**: 字段允许/拒绝列表、模式、数据分类、替换形式和版本。
- **Logging Health Signal**: 写入失败、丢弃、积压和采集延迟。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 代理网关和 Python 服务抽样日志 100% 为单行合法 JSON 且满足必需字段 Schema。
- **SC-002**: 成功、失败、异步、超时和 panic 路径均可通过单一 request_id/correlation_id 关联。
- **SC-003**: 自动敏感信息扫描中密码、验证码、令牌、完整代理/原始 Key、手机号和消息正文泄露数为 0。
- **SC-004**: 日志对非流式代理增加的 P95 延迟小于 5 毫秒，流式连接内存不随事件数线性积累。
- **SC-005**: 日志后端故障注入期间代理仍可服务，丢弃或积压事件 100% 有指标可见。

## Scope

### In Scope

- JSON 日志 Schema、request/correlation ID、跨服务传播、脱敏、错误/panic 记录、保留和日志系统自监控。

### Out of Scope

- 分布式 trace span 全实现、用户行为分析、请求正文审计、前端 Sentry 和外部告警通知。

## Test Requirements

- Schema 测试验证各服务每类日志字段和类型。
- 端到端关联测试覆盖代理、健康检查和用量异步路径。
- 安全扫描使用合成 canary 秘密验证所有正常/错误/panic 路径。
- 故障注入测试覆盖日志后端中断、缓冲满和优雅关闭。
- 性能测试记录日志开销与高流量背压。

## Assumptions

- 依赖 SF01 的共享契约位置；作为横切能力应在其他业务实现早期落地。
- Grafana/Loki 具体查询与看板由 SF19 交付，服务本身以结构化输出为契约。
- request_id 是外部请求主关联标识，correlation_id 用于无单一请求的后台批次。
