# Feature Specification: SF03 用户注册

**Feature ID**: `SF03`  
**Short Name**: `user-registration`  
**Created**: 2026-07-13  
**Status**: Draft  
**Source**: 周度 Spec F02、PRD 角色定义、Python 与数据库规范

## 目标与价值

为 TokenMarket 新用户提供 API 注册能力，建立后续身份认证、角色授权和 Key 所有权的可信账户基础。V0.1 只采集手机号、昵称和角色，不包含实名认证、密码、个人资料页面或角色变更。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 创建唯一账户 (Priority: P1)

作为新用户，我希望提交最少必要信息后获得稳定的用户标识，以便继续登录并使用买家或卖家能力。

**Independent Test**: 使用未注册手机号提交合法注册请求，验证返回用户标识且持久层只有一条账户记录。

**Acceptance Scenarios**:

1. **Given** 手机号未注册且输入合法，**When** 用户提交手机号、昵称和支持的角色，**Then** 系统创建 active 账户并返回用户标识、角色和创建时间。
2. **Given** 用户选择 `buyer`、`seller` 或 `both`，**When** 注册成功，**Then** 账户准确保存所选角色供 SF05 授权。
3. **Given** 注册成功，**When** 查询持久记录，**Then** 标识为 UUID，且审计时间、状态、软删除标记和并发版本完整。

---

### User Story 2 - 安全处理重复与非法注册 (Priority: P1)

作为平台，我希望重复、并发和非法请求不会产生重复账户或泄露已有账户信息。

**Independent Test**: 对同一手机号并发提交多次相同与不同幂等键的请求，验证最多创建一条账户记录。

**Acceptance Scenarios**:

1. **Given** 同一幂等键已经创建账户，**When** 原请求被重放，**Then** 返回与首次一致的结果且不新增记录。
2. **Given** 手机号已经被账户占用，**When** 使用新幂等键再次注册，**Then** 返回资源冲突，不披露账户昵称、角色或状态。
3. **Given** 手机号、昵称或角色不合法，**When** 提交注册，**Then** 返回字段级校验结果且不写入任何账户数据。

### Edge Cases

- 手机号包含空格、国家码、全角字符或不同格式但指向同一号码。
- 昵称仅含空白、超长、包含控制字符或可能污染日志的换行。
- 两个请求在唯一性检查后同时尝试写入同一手机号。
- 幂等键相同但请求体不同。
- 已软删除账户的手机号再次注册。
- 数据库提交成功但响应在到达客户端前中断。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 注册请求 MUST 接收手机号、昵称、角色和幂等键；不得接收由客户端指定的用户 ID 或账户状态。
- **FR-002**: 手机号 MUST 先规范化再进行格式和唯一性校验；规范化规则必须形成可测试契约。
- **FR-003**: 角色 MUST 仅允许 `buyer`、`seller`、`both`，其他值返回参数错误。
- **FR-004**: 昵称 MUST 去除首尾空白，长度为 1–50 个可显示字符，不允许控制字符。
- **FR-005**: 成功注册 MUST 生成 UUID 用户标识并保存 active 状态、创建时间、更新时间、软删除标记和并发版本。
- **FR-006**: 同一规范化手机号在所有可恢复账户中 MUST 唯一；软删除账户不得通过普通注册被静默替换。
- **FR-007**: 相同幂等键和相同请求重放 MUST 返回首次结果；相同幂等键配不同请求体 MUST 返回冲突。
- **FR-008**: 并发注册同一手机号 MUST 最多成功一次，其余请求返回确定的冲突结果。
- **FR-009**: 成功响应 MUST 使用版本化业务接口统一包络，包含 `code`、`message`、`data`、`request_id` 和时间戳。
- **FR-010**: 注册 MUST NOT 签发访问令牌；会话签发属于 SF04。
- **FR-011**: 注册结果和审计日志 MUST NOT 回显完整手机号；面向用户的必要回显应脱敏。

### Engineering Requirements *(mandatory)*

- **ER-001 — Contracts**: 注册契约须进入 OpenAPI；重复手机号映射资源冲突，非法字段映射请求校验错误，响应保持全局错误码规则。
- **ER-002 — Security & Privacy**: 手机号属于个人数据；日志、错误、指标和测试夹具必须脱敏或使用合成号码，服务端拒绝客户端伪造角色外的权限字段。
- **ER-003 — Data Integrity**: PostgreSQL 是账户事实源；规范化手机号唯一约束和幂等约束必须由持久层兜底，写入在单一短事务中完成。
- **ER-004 — Performance & Capacity**: 在正常本地集成环境下，95% 注册请求应在 500 毫秒内完成，不包含外部短信验证。
- **ER-005 — Reliability**: 仅数据库提交成功才返回成功；客户端重试通过幂等键恢复，不对非幂等写入自动重试。
- **ER-006 — Observability**: 记录请求标识、结果码、耗时和脱敏用户标识；手机号冲突率和注册失败率可计量。
- **ER-007 — Accessibility**: V0.1 无前端；错误字段与消息必须机器可读并可被未来无障碍界面正确关联。

### Failure and Recovery Scenarios *(mandatory)*

1. **Given** 数据库在提交前不可用，**When** 用户注册，**Then** 返回可重试的服务错误且不存在部分账户记录。
2. **Given** 两个并发请求注册同一手机号，**When** 唯一约束发生竞争，**Then** 一个成功、其余冲突，且没有未处理异常泄露。
3. **Given** 数据库已提交但客户端未收到响应，**When** 客户端以同一幂等键重试，**Then** 获得原用户标识而不是创建新账户。

### Key Entities

- **User**: 账户事实；关键属性为用户标识、规范化手机号、昵称、角色、状态、审计时间、软删除标记和版本。手机号为个人数据，由 API 用户域拥有。
- **Registration Idempotency Record**: 幂等键、请求摘要、结果用户标识、创建和过期信息；用于安全重放，不保存敏感请求明文。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% 合法注册请求创建且只创建一条账户记录。
- **SC-002**: 对同一手机号发起 100 个并发请求时最多一个成功，不出现重复用户。
- **SC-003**: 相同幂等请求重放 10 次均返回同一用户标识，账户记录数保持 1。
- **SC-004**: 95% 正常注册在 500 毫秒内完成，错误响应均包含可关联请求标识。
- **SC-005**: 自动化日志与响应扫描不出现完整手机号或其他凭证。

## Scope

### In Scope

- 手机号规范化、昵称与角色校验、唯一账户创建、幂等、统一响应和审计元数据。

### Out of Scope

- 手机验证码、令牌签发、密码、实名认证、个人资料编辑、角色变更、前端和管理员账户。

## Test Requirements

- 单元测试覆盖规范化、昵称、角色、错误映射和幂等请求摘要。
- 集成测试使用真实版本兼容数据库验证唯一约束、迁移前进/回退和事务回滚。
- 并发测试验证同手机号竞争和同幂等键重放。
- 安全负面测试验证字段注入、日志脱敏和个人数据不泄露。
- 用户领域变更需达到至少 80% 行覆盖，唯一性和授权相关分支直接覆盖。

## Assumptions

- 依赖 SF01 的服务骨架、契约和测试入口。
- V0.1 已决定允许 `both`，但消费路由必须由 SF05/SF13 排除本人卖家 Key。
- 已删除手机号的再次注册需要独立账户恢复策略，不在普通注册范围。
