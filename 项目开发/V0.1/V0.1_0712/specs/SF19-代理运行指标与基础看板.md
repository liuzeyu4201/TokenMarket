# Feature Specification: SF19 代理运行指标与基础看板

**Feature ID**: `SF19`  
**Short Name**: `proxy-operations-dashboard`  
**Created**: 2026-07-13  
**Status**: Draft  
**Source**: 周度 Spec F10、路线图 V0.1 指标、DevOps 监控规范

## 目标与价值

为开发和运维人员提供 V0.1 代理链路的基础运行可见性：QPS、P95 延迟、4xx/5xx 错误率、活跃/异常 Key、健康检查和用量持久化状态。错误率超过 5% 时生成内部警告事件；V0.1 不发送 PagerDuty、微信或邮件通知。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 在 Grafana 查看代理健康度 (Priority: P1)

作为运维人员，我希望打开一个基础看板即可判断代理是否有流量、是否变慢、是否失败以及是否还有可用 Key。

**Independent Test**: 产生成功、4xx、5xx、慢请求和 Key 状态变化，验证看板所有核心面板在刷新周期内更新。

**Acceptance Scenarios**:

1. **Given** 本地监控环境健康，**When** 访问 Grafana 默认端口 3000，**Then** 能打开 TokenMarket V0.1 代理总览看板。
2. **Given** 代理产生请求，**When** 看板刷新，**Then** 展示按火山方舟聚合的 QPS、P95 端到端/代理附加延迟、4xx 比例和 5xx/上游失败比例。
3. **Given** Key 状态变化，**When** 指标更新，**Then** 看板展示 active、healthy、paused、down、rate_limited、expired 和 invalid 数量。
4. **Given** 健康检查或用量持久化失败，**When** 查看基础看板，**Then** 能看到失败数、积压或最近失败时间。

---

### User Story 2 - 在错误率超过阈值时产生警告 (Priority: P1)

作为维护者，我希望系统失败持续超过 5% 时主动产生可关联警告，避免只能人工盯看板。

**Independent Test**: 在 5 分钟窗口注入超过和低于阈值的系统失败，验证触发、恢复和去抖行为。

**Acceptance Scenarios**:

1. **Given** 过去 5 分钟至少有最小样本量且系统/上游失败率持续超过 5%，**When** 规则评估，**Then** 产生 WARN/P1 内部警告事件，包含服务、窗口、比率、影响和排查入口。
2. **Given** 仅用户输入错误或无效代理 Key 导致 4xx，**When** 计算系统错误率，**Then** 不把可预期客户端错误计入 5% 系统失败告警。
3. **Given** 错误率恢复到阈值以下，**When** 持续一个评估周期，**Then** 警告进入 resolved，并避免每次采样重复刷屏。

---

### User Story 3 - 识别服务和容量不可用 (Priority: P2)

作为运维人员，我希望区分服务宕机、无可用 Key、Key 满载和计量积压，以采取正确措施。

**Acceptance Scenarios**:

1. **Given** 服务 liveness 失败或 readiness 失败，**When** 查看看板，**Then** 状态和失败依赖可区分。
2. **Given** 可用 Key 数为零或容量拒绝持续增长，**When** 查看看板，**Then** 能在 5 分钟内识别供给或容量问题。

### Edge Cases

- 低流量窗口只有一两个失败导致百分比失真。
- 指标进程重启导致计数器归零。
- 指标标签包含 request_id、用户 ID 或 key_id 造成高基数。
- Grafana 可访问但数据源或 Dashboard provisioning 失败。
- 监控采集自身中断，旧数据看似“正常”。
- 4xx、5xx、上游 429、路由 503 的口径混淆。
- 告警状态在阈值附近反复抖动。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 每个可部署服务 MUST 暴露独立 liveness 和 readiness；readiness 必须反映接收本服务关键请求所需的依赖。
- **FR-002**: 代理网关 MUST 提供 Prometheus-compatible 指标，至少覆盖请求数、状态/错误类别、延迟分布、活跃连接/流和容量拒绝。
- **FR-003**: Key 指标 MUST 覆盖 active、healthy、paused、down、rate_limited、expired、invalid 和可路由数量，按 platform/status 聚合。
- **FR-004**: 健康检查指标 MUST 覆盖运行数、成功、失败类别、状态转换、恢复、耗时和调度延迟。
- **FR-005**: 用量指标 MUST 覆盖观察产生、持久化成功/失败、积压、重复、冲突、估算和对账差异。
- **FR-006**: Grafana 基础看板 MUST 至少包含 QPS、P95 延迟、4xx/5xx 错误率和活跃 Key 数四个核心面板，并增加健康检查与用量失败面板。
- **FR-007**: 看板 MUST 显示当前值与近期趋势，默认刷新不慢于 10 秒，并标明时间范围和数据更新时间。
- **FR-008**: 系统错误率 MUST 定义为 5xx、502/503/504、内部异常和不可预期上游失败占全部合格代理请求比例；可预期认证/参数 4xx 不计入 5% 告警分子。
- **FR-009**: 过去 5 分钟系统错误率持续 >5% 且样本至少 20 个请求时 MUST 产生 WARN/P1 内部警告；恢复阈值采用低于 3% 持续 5 分钟以避免抖动。
- **FR-010**: 警告事件 MUST 包含规则、严重度、服务、开始/恢复时间、当前值、阈值、影响说明、责任人/运行手册引用和安全关联线索。
- **FR-011**: V0.1 警告 MUST 出现在结构化日志和 Grafana 告警状态中，不发送外部邮件、PagerDuty、微信或 Webhook。
- **FR-012**: 指标标签 MUST 使用有界枚举，不得包含用户 ID、request_id、完整/脱敏 Key 字符串、手机号或模型消息。
- **FR-013**: Dashboard 和规则配置 MUST 可版本控制、自动加载并在全新环境重建，不依赖手工点击保存。
- **FR-014**: 监控采集缺失 MUST 显式展示 no data/采集失败，不得把缺失数据渲染为零和健康。

### Engineering Requirements *(mandatory)*

- **ER-001 — Contracts**: 指标名称、单位、标签、直方图区间、错误口径和告警状态机须形成版本化监控契约。
- **ER-002 — Security & Privacy**: 指标和看板不得含凭证、个人数据、高基数资源 ID；管理访问需限制在批准环境。
- **ER-003 — Data Integrity**: 计数器只单调增加并正确处理重启；百分比有最小样本量和 no-data 语义，统计口径在文档中固定。
- **ER-004 — Performance & Capacity**: 指标采集对代理吞吐和 P95 的开销小于 2%；Dashboard 常用查询在 5 秒内返回。
- **ER-005 — Reliability**: 指标端点、采集、存储和 Grafana 数据源各自有健康信号；看板和规则可从版本控制恢复。
- **ER-006 — Observability**: 监控系统监控自身采集失败、规则评估失败、数据源错误和告警通知状态，并指定 V0.1 运维所有者。
- **ER-007 — Accessibility**: 看板不能只用红/绿色表达状态；面板提供文字、数值、阈值和一致单位，支持键盘导航和可读标题。

### Failure and Recovery Scenarios *(mandatory)*

1. **Given** 指标采集停止，**When** 看板查询，**Then** 显示 no data/采集异常并产生监控自检信号，不显示健康零值。
2. **Given** 错误率在阈值附近抖动，**When** 规则评估，**Then** 使用持续窗口与恢复阈值避免重复 firing/resolved。
3. **Given** Grafana 配置丢失或环境重建，**When** 重新部署版本化配置，**Then** 数据源、Dashboard 和规则自动恢复且查询可用。

### Key Entities

- **Metric Definition**: 名称、类型、单位、标签、来源、帮助文本和所有者。
- **Dashboard Definition**: 版本化面板、查询、阈值、刷新和 no-data 语义。
- **Alert Rule/Incident State**: 窗口、分子/分母、阈值、最小样本、持续时间、严重度、责任人和 firing/resolved 状态。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Grafana 端口 3000 可访问，六类核心信息（QPS、P95、错误率、Key 状态、健康检查、用量持久化）均有当前值和趋势。
- **SC-002**: 所有测试流量变化在 10 秒内反映到看板。
- **SC-003**: >5% 且满足样本/持续时间的系统错误场景 100% 触发，纯客户端 4xx 场景误报数为 0。
- **SC-004**: 恢复到 <3% 持续 5 分钟后警告 100% resolved，阈值抖动不产生重复事件风暴。
- **SC-005**: 指标采集对代理吞吐和 P95 开销小于 2%，常用 Dashboard 查询 5 秒内返回。
- **SC-006**: 指标标签扫描不出现凭证、个人数据或无界 request/user/key ID。

## Scope

### In Scope

- 服务健康、代理/Key/健康检查/用量指标、Grafana 基础看板、5% 内部错误率警告和监控自检。

### Out of Scope

- 外部通知、值班排班、自动扩缩容、业务 GMV/收入看板、用户前端、分布式 tracing UI。

## Test Requirements

- 指标契约测试验证名称、类型、单位、标签和无高基数。
- Dashboard provisioning 冒烟测试验证全新环境自动加载和查询。
- 告警规则测试覆盖阈值、最小样本、持续时间、恢复和 4xx 排除。
- 故障注入覆盖 no data、数据源错误、服务不 ready 和 Key 池归零。
- 性能测试验证监控开销和查询时延。

## Assumptions

- 依赖 SF12、SF13、SF16、SF17、SF18 提供业务与日志信号。
- SF02 提供本地 Grafana；监控数据源具体部署由实施计划确定。
- V0.1 只有火山方舟，platform 标签仍保留以维持契约扩展性。
